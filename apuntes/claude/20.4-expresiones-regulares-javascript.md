# Expresiones regulares en JavaScript

Programación IV: Desarrollo Web — Etapa 1, fundamentos técnicos
Apunte complementario de la unidad de JavaScript

Hasta ahora buscaste contenido exacto. `texto.includes("hola")` pregunta si esas cuatro letras están ahí.

Pero casi nada de lo que necesitás validar en una aplicación web tiene contenido exacto. Un email no es una cadena concreta: es cualquier cadena con arroba en el medio y un punto después. Un teléfono no es un número fijo: es cualquier secuencia de dígitos con espacios, guiones y paréntesis salpicados. Una fecha, un CUIT, un código postal, un nombre de archivo: todos son una forma, no un valor.

Las expresiones regulares son el lenguaje para describir formas. Este apunte arranca por lo que son, sigue por cómo se escriben, explica cómo funciona el motor por dentro y termina en recetas que vas a copiar al proyecto de la materia.

## Qué es una expresión regular

Una expresión regular describe un conjunto de cadenas.

Conviene tomar esa definición literal. La expresión `/ab/` no es una instrucción para buscar. Es el nombre de un conjunto con un solo elemento: la cadena `"ab"`. La expresión `/ab*/` nombra un conjunto infinito: `"a"`, `"ab"`, `"abb"`, `"abbb"` y así para siempre.

Cuando escribís `patron.test(texto)` no le pedís al motor que busque. Le preguntás si alguna parte de `texto` pertenece al conjunto que nombra `patron`. Todo lo demás son variaciones de esa misma pregunta: dónde empieza la parte que pertenece, cuáles son todas las partes que pertenecen, con qué reemplazarlas.

Pensarlas como conjuntos evita el error más común, que es leerlas como si fueran un programa que camina el texto. El motor sí camina el texto, y más adelante vamos a ver cómo, pero el significado de la expresión no depende de ese recorrido.

## Las tres operaciones que generan todo

Toda la sintaxis, con sus decenas de símbolos, sale de tres operaciones sobre conjuntos. Si entendés las tres, el resto es notación abreviada.

Concatenación: pegar un conjunto después de otro. Si un conjunto tiene `"a"` y el otro tiene `"b"`, la concatenación tiene `"ab"`. Se escribe poniendo las cosas una al lado de la otra.

```javascript
/ab/.test("ab");     // true
/ab/.test("ba");     // false
```

Alternancia: la unión de dos conjuntos. Se escribe con la barra vertical.

```javascript
/gato|perro/.test("tengo un perro");   // true
```

Repetición: todas las repeticiones de un conjunto, incluida la vacía. Se escribe con el asterisco.

```javascript
/ab*/.test("a");      // true, cero repeticiones de b
/ab*/.test("abbb");   // true
```

Con esas tres alcanza para describir cualquier lenguaje regular. Falta una pieza de notación, no de teoría: los paréntesis, que sirven para decir a qué se aplica cada operación.

```javascript
/gato|perros/;      // gato, o perros
/(gato|perro)s/;    // gatos, o perros
/ab*/;              // a seguida de cero o más b
/(ab)*/;            // cero o más repeticiones de ab
```

El asterisco y la barra tienen precedencia distinta, igual que la multiplicación y la suma. La repetición se aplica al último elemento; la alternancia parte la expresión entera en dos. Cuando dudes, poné paréntesis.

## Cómo se escribe una expresión regular en JavaScript

Hay dos formas de crear el objeto.

El literal va entre barras y se compila cuando el archivo se carga:

```javascript
const patron = /\d+/g;
```

El constructor recibe una cadena y se compila en tiempo de ejecución:

```javascript
const patron = new RegExp("\\d+", "g");
```

Las dos producen un objeto `RegExp` idéntico. La diferencia práctica es el escape. En el literal escribís la expresión tal cual. En el constructor la expresión viaja dentro de una cadena, así que las barras invertidas de la expresión hay que duplicarlas: la cadena `"\\d"` contiene los dos caracteres que el motor necesita ver.

Usá el literal siempre que el patrón sea fijo. Usá el constructor solo cuando el patrón se arma en tiempo de ejecución, típicamente porque una parte viene de una variable:

```javascript
function buscarPalabra(texto, palabra) {
  const patron = new RegExp(`\\b${palabra}\\b`, "iu");
  return patron.test(texto);
}
```

Ese código tiene un problema que vamos a arreglar más adelante: si `palabra` trae un punto, un paréntesis o un asterisco, esos caracteres no se buscan literalmente, se interpretan como sintaxis.

## Cómo se hace la pregunta

El patrón por sí solo no hace nada. Hay siete formas de consultarlo y cada una responde una pregunta distinta.

`test` devuelve si hay al menos una coincidencia. Es la que querés para validar:

```javascript
/^\d{4}$/.test("2026");    // true
```

`search` devuelve la posición de la primera coincidencia, o -1:

```javascript
"pedido 4471".search(/\d/);    // 7
```

`match` sin la bandera `g` devuelve la primera coincidencia con todo su detalle: el texto que coincidió, los grupos, la posición. Con la bandera `g` devuelve solo el arreglo de textos que coincidieron, sin detalle:

```javascript
"tel 4451-2233".match(/(\d{4})-(\d{4})/);
// ["4451-2233", "4451", "2233", index: 4, ...]

"a1 b2 c3".match(/\d/g);
// ["1", "2", "3"]
```

`matchAll` devuelve todas las coincidencias con todo su detalle. Exige la bandera `g` y devuelve un iterador, así que se recorre con `for of` o se expande con el operador de propagación:

```javascript
for (const m of "a1 b2".matchAll(/(\w)(\d)/g)) {
  console.log(m[1], m[2], m.index);
}
```

`replace` reemplaza la primera coincidencia, o todas si el patrón tiene `g`. `replaceAll` reemplaza todas y exige `g` cuando le pasás una expresión regular:

```javascript
"  hola   mundo  ".replace(/\s+/g, " ").trim();   // "hola mundo"
```

`split` parte la cadena usando el patrón como separador:

```javascript
"uno, dos ,tres".split(/\s*,\s*/);   // ["uno", "dos", "tres"]
```

`exec` es la forma cruda: devuelve una coincidencia por llamada y avanza. Sirve para recorridos manuales, pero `matchAll` cubre casi todos los casos con menos filo.

### El objeto con estado

Un patrón con la bandera `g` o `y` guarda una propiedad `lastIndex` y la modifica cada vez que lo usás con `test` o `exec`. Esto sorprende a todo el mundo una vez:

```javascript
const patron = /a/g;
patron.test("aa");   // true, lastIndex queda en 1
patron.test("aa");   // true, lastIndex queda en 2
patron.test("aa");   // false, y lastIndex vuelve a 0
```

La regla práctica es simple: no reutilices un patrón con `g` para validar. Declaralo sin `g` si vas a usar `test`, o creá el literal dentro de la función. Un patrón con `g` declarado como constante en el módulo y usado en un bucle de validación es un error difícil de encontrar, porque falla de forma intermitente.

## Clases de caracteres

Los corchetes nombran un conjunto de un solo carácter. Adentro, casi todos los símbolos pierden su significado especial.

```javascript
/[aeiou]/;        // una vocal
/[a-z]/;          // una letra minúscula, por rango
/[a-zA-Z0-9]/;    // varios rangos juntos
/[^0-9]/;         // cualquier carácter que no sea un dígito
```

El acento circunflejo al principio niega la clase. En cualquier otra posición es un carácter común. El guion es un rango entre dos caracteres, salvo al principio o al final, donde es un guion literal: `[-+]` son los dos signos.

Hay atajos para las clases más usadas:

| atajo | equivale a | significado |
|---|---|---|
| `\d` | `[0-9]` | dígito |
| `\D` | `[^0-9]` | no dígito |
| `\w` | `[A-Za-z0-9_]` | carácter de palabra |
| `\W` | `[^A-Za-z0-9_]` | no carácter de palabra |
| `\s` | espacios, tabulaciones, saltos de línea | espacio en blanco |
| `\S` | lo contrario | no espacio en blanco |

Fijate que `\w` es ASCII puro. No incluye la eñe ni las vocales acentuadas. Para texto en castellano, `\w` es casi siempre la elección equivocada; más abajo está la alternativa.

El punto es una clase especial: coincide con cualquier carácter menos los saltos de línea. Con la bandera `s` también coincide con los saltos. Dentro de los corchetes el punto es un punto literal, así que `[.]` y `\.` son lo mismo.

## Cuantificadores

Los cuantificadores repiten lo que tienen a la izquierda.

```javascript
/a?/;        // cero o una
/a*/;        // cero o más
/a+/;        // una o más
/a{3}/;      // exactamente tres
/a{2,}/;     // dos o más
/a{2,5}/;    // entre dos y cinco
```

Todos son codiciosos: agarran la mayor cantidad posible y después devuelven caracteres si hace falta para que el resto de la expresión funcione. Agregarles un signo de pregunta los vuelve perezosos: agarran la menor cantidad posible y van sumando solo si hace falta.

La diferencia se ve mejor con un ejemplo. Sobre el texto `"<b>hola</b>"`:

```javascript
"<b>hola</b>".match(/<.+>/)[0];    // "<b>hola</b>"
"<b>hola</b>".match(/<.+?>/)[0];   // "<b>"
```

El codicioso se comió todo hasta el último `>` y funcionó igual, porque quedaba un `>` para cerrar. El perezoso se detuvo en el primero. Cuando extraés algo delimitado, casi siempre querés el perezoso.

## Anclas y bordes

Las anclas no consumen caracteres. Afirman algo sobre la posición.

`^` afirma que estás al principio del texto. `$` afirma que estás al final. Con la bandera `m` pasan a valer por línea en vez de por texto completo.

Esta distinción es la diferencia entre buscar y validar:

```javascript
/\d{4}/.test("abc 2026 def");     // true, hay cuatro dígitos ahí
/^\d{4}$/.test("abc 2026 def");   // false, el texto entero no es cuatro dígitos
```

Toda validación de formulario lleva `^` y `$`. Sin ellos, cualquier basura alrededor pasa el control.

`\b` afirma un borde de palabra: la posición donde un `\w` toca un no `\w`. Sirve para buscar una palabra completa:

```javascript
/\bsol\b/.test("hace sol");        // true
/\bsol\b/.test("solamente");       // false
```

Y acá se cobra que `\w` sea ASCII. Como la eñe y las acentuadas no son caracteres de palabra para el motor, los bordes caen en lugares raros:

```javascript
/\bcafé\b/.test("tomé café con leche");   // false
```

Falla porque entre la `é` y el espacio no hay transición: los dos son no palabra, así que no hay borde. Para texto en castellano conviene evitar `\b` y usar miradas, que están más abajo.

## Grupos

Los paréntesis, además de agrupar para la precedencia, capturan lo que coincidió adentro. Se numeran de izquierda a derecha por el paréntesis que abre, empezando en 1.

```javascript
const m = "2026-08-24".match(/(\d{4})-(\d{2})-(\d{2})/);
m[0];   // "2026-08-24"
m[1];   // "2026"
m[2];   // "08"
```

Los grupos con nombre se leen mucho mejor y no se rompen cuando agregás un paréntesis en el medio:

```javascript
const patron = /(?<anio>\d{4})-(?<mes>\d{2})-(?<dia>\d{2})/;
const { anio, mes, dia } = "2026-08-24".match(patron).groups;
```

Si agrupás solo por precedencia y no necesitás el contenido, usá el grupo sin captura. Es más claro y evita numeración inútil:

```javascript
/(?:ab)+/;
```

Una referencia hacia atrás pide que algo se repita igual, no que tenga la misma forma:

```javascript
/(\w)\1/.test("aa");           // true
/(\w)\1/.test("ab");           // false
/(?<c>\w)\k<c>/.test("aa");    // true, con nombre
```

En el reemplazo, los grupos vuelven como `$1`, `$2` o `$<nombre>`:

```javascript
"2026-08-24".replace(/(\d{4})-(\d{2})-(\d{2})/, "$3/$2/$1");
// "24/08/2026"
```

Y si el reemplazo necesita lógica, pasale una función. Recibe la coincidencia, los grupos, la posición y el texto completo:

```javascript
"precio: 1200".replace(/\d+/g, (n) => Number(n) * 1.21);
// "precio: 1452"
```

## Miradas

Una mirada afirma qué hay alrededor sin consumirlo. Son cuatro y se leen como su nombre indica.

```javascript
/hola(?=\s)/;      // hola, si le sigue un espacio
/hola(?!\s)/;      // hola, si no le sigue un espacio
/(?<=\$)\d+/;      // dígitos, si vienen después de un signo pesos
/(?<!\$)\d+/;      // dígitos, si no vienen después de un signo pesos
```

Lo que está adentro de la mirada no forma parte de la coincidencia. Por eso sirven para recortar con precisión:

```javascript
"vale $1200".match(/(?<=\$)\d+/)[0];   // "1200", sin el signo
```

Y también para pedir varias condiciones sobre el mismo texto al mismo tiempo, porque cada mirada empieza a evaluar desde la misma posición:

```javascript
const segura = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,}$/;
segura.test("Contra1234");    // true
segura.test("contra1234");    // false, falta mayúscula
```

Esa es la forma idiomática de validar una contraseña con varias reglas. Cada mirada es una regla independiente y las agregás o quitás sin tocar el resto.

## Banderas

Las banderas van después de la barra de cierre y cambian el modo de trabajo del motor.

| bandera | efecto |
|---|---|
| `g` | busca todas las coincidencias, no solo la primera |
| `i` | ignora mayúsculas y minúsculas |
| `m` | `^` y `$` valen por línea |
| `s` | el punto también coincide con saltos de línea |
| `u` | modo Unicode, habilita `\p{...}` |
| `v` | modo Unicode extendido, con operaciones entre clases |
| `y` | modo pegajoso, la coincidencia debe empezar en `lastIndex` |
| `d` | agrega las posiciones de inicio y fin de cada grupo |

La bandera `y` sirve para escribir analizadores léxicos, donde cada token tiene que empezar exactamente donde terminó el anterior. La bandera `d` sirve para resaltar coincidencias en pantalla, porque te da los índices de cada grupo y no solo el texto.

## Unicode

Sin la bandera `u`, el motor trabaja con unidades de código de 16 bits. Cualquier carácter fuera del plano básico, como un emoji o una letra de un alfabeto extendido, ocupa dos unidades y el punto coincide con la mitad.

```javascript
"😀".length;               // 2
"😀".match(/./)[0].length;  // 1, media coincidencia
"😀".match(/./u)[0].length; // 2, el carácter completo
```

Con `u` habilitás además las propiedades Unicode, que son la respuesta correcta al problema de `\w` y el castellano:

```javascript
/^\p{L}+$/u.test("Núñez");           // true, solo letras
/^\p{Lu}/u.test("Núñez");            // true, empieza con mayúscula
/^[\p{L}\p{Nd}]+$/u.test("año2026"); // letras y dígitos de cualquier alfabeto
```

Las propiedades más útiles para validar datos de personas son `\p{L}` para letras, `\p{Lu}` y `\p{Ll}` para mayúsculas y minúsculas, `\p{Nd}` para dígitos decimales, `\p{P}` para puntuación y `\p{Diacritic}` para los signos que se combinan con una letra.

La bandera `v`, más reciente, agrega operaciones entre clases. La diferencia con `--` y la intersección con `&&` evitan clases enormes escritas a mano:

```javascript
/^[\p{L}--\p{Script=Han}]+$/v;   // letras, menos las chinas
```

Poné siempre `u` cuando el texto venga de un usuario. No cuesta nada y evita una familia entera de errores.

## Cómo funciona el motor por dentro

Hasta acá vimos qué significa cada símbolo. Ahora hace falta el modelo mecánico, porque explica tanto los límites como los problemas de rendimiento.

El modelo teórico de una expresión regular es un autómata finito: una máquina con una cantidad fija de estados que lee el texto de izquierda a derecha, un carácter por vez, y cambia de estado según lo que lee. No tiene memoria más allá del estado en el que está.

De ahí sale el límite más importante: una expresión regular no puede contar. No puede verificar que los paréntesis de una fórmula estén balanceados, porque para eso necesitaría llevar la cuenta de cuántos abrió, y esa cuenta no tiene límite. No puede validar HTML anidado por la misma razón. Cada vez que alguien intenta, escribe un monstruo de 200 caracteres que funciona con los casos que probó y falla con el siguiente.

La regla es clara: si la estructura se anida sin límite, necesitás un analizador, no una expresión regular. Para HTML usá el DOM. Para JSON usá `JSON.parse`. Para CSV con comillas usá una librería.

El motor de JavaScript, además, no es un autómata puro. Implementa la búsqueda con retroceso: prueba una alternativa, y si más adelante falla, vuelve atrás y prueba la siguiente. Ese retroceso es lo que permite las referencias hacia atrás y las miradas, que un autómata puro no puede expresar. También es lo que puede hacer explotar el tiempo de ejecución.

### Retroceso catastrófico

Cuando dos cuantificadores anidados describen el mismo texto de muchas formas distintas, la cantidad de combinaciones que el motor prueba antes de rendirse crece de forma exponencial.

```javascript
const malo = /^(a+)+$/;
malo.test("aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!");
```

Con 30 caracteres, ese `test` puede tardar varios segundos. Con 40, minutos. El texto no coincide por el signo de admiración final, pero antes de saberlo el motor prueba todas las maneras de repartir 30 letras `a` entre los dos cuantificadores.

En el navegador congela una pestaña. En el servidor es peor: Node ejecuta el patrón en el hilo principal, así que una sola petición con un texto armado a propósito deja de responder a todas las demás. El ataque tiene nombre propio, ReDoS, y es de los más fáciles de meter sin darse cuenta.

Las señales de alarma son tres: un cuantificador dentro de otro, alternativas que pueden coincidir con lo mismo, y patrones armados con datos del usuario. La corrección casi siempre es simplificar:

```javascript
const bueno = /^a+$/;    // describe el mismo conjunto, sin ambigüedad
```

Cuando el patrón viene de afuera, validá que el texto de entrada tenga un largo máximo antes de aplicarlo, y desconfiá de cualquier expresión regular que aceptes como configuración.

## Escapar texto literal

Volvamos al problema que dejamos pendiente. Si insertás texto del usuario dentro de un patrón, sus caracteres especiales se interpretan como sintaxis. Un punto pasa a coincidir con cualquier cosa, y un paréntesis suelto rompe la compilación con un error.

Los runtimes recientes traen `RegExp.escape`, que resuelve esto en una línea. Si no podés contar con él, la función es corta:

```javascript
function escapar(texto) {
  return texto.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
}

const patron = new RegExp(escapar(entradaDelUsuario), "giu");
```

El `$&` en el reemplazo significa la coincidencia completa, así que cada carácter especial queda precedido por una barra invertida.

## Recetas para el proyecto de la materia

Estas son las que vas a necesitar en la agenda de contactos. Están pensadas para copiarse, pero leé la advertencia de cada una.

Email, versión pragmática:

```javascript
const EMAIL = /^[^\s@]+@[^\s@]+\.[^\s@]{2,}$/;
```

No intentes escribir el email perfecto. La definición formal del estándar admite comillas, comentarios y direcciones que ningún sistema real acepta, y la expresión que la cubre entera tiene miles de caracteres. Lo único que un patrón puede darte es un filtro de errores de tipeo. La única validación real de un email es mandarle un correo.

Teléfono argentino, normalizando primero:

```javascript
function normalizarTelefono(texto) {
  const soloDigitos = texto.replace(/\D/g, "");
  return /^(?:54)?9?\d{10}$/.test(soloDigitos) ? soloDigitos : null;
}
```

La estrategia general es esa: primero limpiás con `replace`, después validás sobre el resultado limpio. Un patrón que acepte todas las formas de escribir un teléfono, con y sin código de país, con paréntesis, guiones o espacios, es inmantenible.

Fecha en formato ISO:

```javascript
const ISO = /^(?<anio>\d{4})-(?<mes>\d{2})-(?<dia>\d{2})$/;

function parsearFecha(texto) {
  const m = ISO.exec(texto);
  if (!m) return null;
  const { anio, mes, dia } = m.groups;
  const fecha = new Date(Number(anio), Number(mes) - 1, Number(dia));
  return fecha.getMonth() === Number(mes) - 1 ? fecha : null;
}
```

Acá está la lección más importante de todo el apunte, así que vale repetirla. La expresión regular valida la forma, no la validez. `"2026-02-31"` tiene forma perfecta y no existe. La forma la controla el patrón; la validez la controla el código.

Lo mismo pasa con el CUIT. El patrón `/^\d{2}-?\d{8}-?\d$/` verifica la forma, pero el dígito verificador se calcula, y ese cálculo no se puede escribir como expresión regular.

Nombre de persona, sin ASCII de por medio:

```javascript
const NOMBRE = /^\p{Lu}\p{L}+(?:[ '-]\p{Lu}?\p{L}+)*$/u;
NOMBRE.test("María del Carmen");   // true
NOMBRE.test("O'Brien");            // true
```

Espacios de más en cualquier campo de texto:

```javascript
const limpio = entrada.trim().replace(/\s+/g, " ");
```

Convertir un título en identificador para la URL:

```javascript
function aSlug(texto) {
  return texto
    .normalize("NFD")
    .replace(/\p{Diacritic}/gu, "")
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "");
}

aSlug("Programación IV: Desarrollo Web");   // "programacion-iv-desarrollo-web"
```

La normalización a NFD separa cada letra acentuada en letra más acento, y recién entonces se pueden borrar los acentos con una propiedad Unicode.

Extraer datos de texto libre, con `matchAll`:

```javascript
const texto = `
Ana Pérez - ana@ejemplo.com - 4451-2233
Luis Gómez - luis@ejemplo.com - 4452-8877
`;

const LINEA = /^(?<nombre>.+?) - (?<email>\S+@\S+) - (?<tel>[\d-]+)$/gmu;
const contactos = [...texto.matchAll(LINEA)].map((m) => m.groups);
```

Tres cosas que hacen funcionar ese patrón: la bandera `m` hace que `^` y `$` valgan por línea, el `+?` perezoso en el nombre evita que se coma los guiones separadores, y los grupos con nombre te dan un objeto listo para usar.

Resaltar una búsqueda del usuario en una lista de resultados:

```javascript
function resaltar(texto, busqueda) {
  const patron = new RegExp(`(${escapar(busqueda)})`, "giu");
  return texto.replace(patron, "<mark>$1</mark>");
}
```

Esa función combina casi todo el apunte: escape de texto literal, constructor con patrón dinámico, banderas de búsqueda global e insensible a mayúsculas, grupo de captura y referencia en el reemplazo.

## Cómo depurar una expresión que no funciona

Cuando un patrón falla, no lo mires fijo. Trabajalo.

Partilo en pedazos y probá cada uno por separado. Si `/^(?<a>\d+)-(?<b>\w+)$/` no coincide, probá primero `/^\d+/`, después `/-/`, después el resto.

Armalo por partes con el constructor, que admite comentarios y saltos de línea en el código fuente:

```javascript
const anio = "\\d{4}";
const mes = "\\d{2}";
const ISO = new RegExp(`^${anio}-${mes}-${mes}$`);
```

Usá grupos con nombre desde el principio. Un `m.groups.mes` que sale `undefined` te dice exactamente qué parte no coincidió; un `m[3]` no te dice nada.

Y desconfiá de tu patrón cuando funciona. Probalo con la entrada vacía, con espacios al principio y al final, con acentos, con un texto diez veces más largo del esperado y con el caso que creés imposible. La mayoría de los patrones que fallan en producción pasaron todas las pruebas del autor.

## Ejercicios

1. Escribí tres expresiones regulares que describan el mismo conjunto de cadenas: las que tienen entre 2 y 4 letras `a` seguidas. Explicá cuál preferís y por qué.
2. Explicá sin ejecutar por qué `/^\d+$/.test("12\n")` devuelve `true` en algunos motores y qué agregarías para evitar la sorpresa. Verificalo después.
3. Escribí una función `contarPalabras(texto)` que funcione bien con texto en castellano, incluidas las palabras con eñe y con acento. No uses `\w`.
4. Dado el texto `"total: $1.200,50 y envío: $300"`, extraé los dos importes como números de JavaScript. Vas a necesitar una mirada, un reemplazo y una conversión.
5. Explicá por qué `/^(\d+)*$/` es peligrosa y escribí una expresión equivalente que no lo sea. Medí las dos con `console.time` sobre una cadena de 30 dígitos terminada en una letra.
6. Escribí `validarCuit(texto)` que acepte las formas `20-12345678-3` y `20123456783`, y que además verifique el dígito verificador. Decidí qué parte resuelve la expresión regular y qué parte resuelve el código.
7. Escribí `plantilla(texto, datos)` que reemplace cada `{{clave}}` del texto por `datos[clave]`, y que deje intacto el marcador si la clave no existe. Usá una función de reemplazo y un grupo con nombre.
8. Tomá el patrón de contactos de la sección de recetas y hacelo tolerante: que acepte teléfono ausente, espacios de más alrededor de los guiones separadores y líneas vacías intercaladas.
