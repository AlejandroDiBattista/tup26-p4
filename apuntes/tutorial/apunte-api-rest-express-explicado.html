UNIDAD 01 / 09 · DIAPOSITIVAS 2–9

HTTPEntender el intercambio

Antes de escribir una ruta, identificá qué recibe el servidor y qué tiene que devolver. El apunte empieza con Node sin Express para hacer visible ese trabajo.

02

Un servidor espera y responde

Apunte ↗

En el intercambio HTTP que muestra el apunte, el cliente inicia un pedido y el servidor produce la respuesta. El cliente puede ser el navegador, una aplicación o curl: la API no depende de una interfaz visual particular.

El puerto 3000 identifica dónde escucha este servidor de demostración. Escribí el recorrido en dos direcciones: qué pide el cliente y qué devuelve el servidor. Todavía no hace falta hablar de contactos ni de archivos.

03

Un pedido es texto

Apunte ↗

Leé el ejemplo de arriba abajo. POST /contactos HTTP/1.1 identifica la operación. Los encabezados agregan información al mensaje; Content-Type: application/json declara el formato del cuerpo.

La línea vacía separa los encabezados de los datos. El objeto con nombre y teléfono está en el cuerpo: no es un parámetro de la URL. El ejemplo del apunte es una representación textual de un mensaje HTTP/1.1; no tenés que redactar estos encabezados a mano cuando usás fetch o curl.

04

La respuesta trae un código de estado

Apunte ↗

La respuesta comienza con el resultado de la operación: 201 Created. Luego declara que devuelve JSON y señala en Location la URL del recurso creado.

El cuerpo incluye el id asignado por el servidor. El cliente envió datos para crear un contacto y recibió su representación identificada. No confundas Location, que es un encabezado, con una propiedad del JSON.

Ver el ejemplo del apunteDiapositiva 04

Content-Type dice en qué formato viene el cuerpo.

05

La primera cifra dice qué pasó

Apunte ↗

El apunte usa la primera cifra para leer rápidamente una respuesta: éxito, familia 3xx, problema en el pedido o fallo del servidor. En el CRUD que vamos a construir aparecen sobre todo 200, 201, 204, 400, 404 y 500.

La familia orienta, pero el código concreto completa el significado. Esta clase no implementa los ejemplos 301, 304 ni 409 de la tabla; se conservan como referencia del apunte, no como respuestas de nuestras rutas.

Ver el ejemplo del apunteDiapositiva 05
2xxsalió bien200 201 204
3xxel recurso está en otro lado301 304
4xxel cliente se equivocó400 404 409
5xxel servidor falló500

Un 4xx pide corregir el pedido. Un 5xx dice que el problema es nuestro.

06

Un servidor con Node solo

Apunte ↗

http.createServer recibe una función que Node ejecutará por cada pedido. req representa la entrada y res permite construir la salida.

writeHead establece el estado y el encabezado. end termina la respuesta con el texto. listen pone el servidor a escuchar: registrar la función no es lo mismo que atender ya un pedido. Este bloque sí es un primer programa completo.

Ver el ejemplo del apunteDiapositiva 06

Node ejecuta la función una vez por cada pedido.

07

Decidir según método y ruta

Apunte ↗

Sin Express, el programa compara el método y la ruta. Para listar necesita reconocer GET /contactos; para obtener uno, extrae el número de una URL como /contactos/2.

La expresión regular reconoce la forma y captura el identificador. Después hay que convertirlo a número y buscarlo. El bloque es un fragmento del manejador anterior, no otro servidor completo. Los puntos suspensivos del comentario anuncian una respuesta todavía por completar.

Ver el ejemplo del apunteDiapositiva 07
08

El cuerpo llega en trozos

Apunte ↗

El cuerpo no aparece directamente como objeto JavaScript. El ejemplo recorre los trozos del pedido, acumula el texto y recién después llama a JSON.parse.

Esta versión inicial no incorpora protección para un JSON mal formado, y el apunte señala ese problema. Tampoco es la versión final del generador de identificadores ni de la validación: se muestra para entender el trabajo que se está haciendo manualmente.

Ver el ejemplo del apunteDiapositiva 08

Si el JSON viene mal formado, JSON.parse lanza y el servidor se cae.

09

Todo esto se repite

Apunte ↗

Lo repetitivo no es la regla de negocio de una agenda: es el trabajo de atender HTTP. Reconocer rutas, extraer parámetros, leer el cuerpo y serializar respuestas aparece una y otra vez.

Express organiza ese trabajo sin reemplazar Node. A partir de aquí expresaremos las rutas y dejaremos de escribir un árbol manual de condiciones para cada pedido.

Ver el ejemplo del apunteDiapositiva 09
  • un if por cada ruta, y el orden importa
  • una expresión regular para sacar el id
  • el cuerpo se junta a mano
  • JSON.parse sin protección
  • writeHead y JSON.stringify en cada respuesta

Express ordena este trabajo. Usa http por debajo.

UNIDAD 02 / 09 · DIAPOSITIVAS 10–15

RESTDiseñar el contrato

Ahora ponemos nombres a los recursos. La combinación de método y URL expresa la operación; el código de estado y el cuerpo expresan el resultado.

10

Las URL son sustantivos

Apunte ↗

La URL nombra aquello sobre lo que trabajamos: /contactos es la colección y /contactos/3 identifica un elemento. El verbo HTTP indica si queremos consultar, crear o borrar.

Por eso no hace falta poner obtener o borrar en el nombre. En la comparación del apunte, GET /borrarContacto mezcla una consulta con una acción que modifica datos. El contrato propuesto separa esas responsabilidades.

Ver el ejemplo del apunteDiapositiva 10

Nombran recursos. El método dice qué hacer con ellos.

11

La API de la agenda

Apunte ↗

Usá esta tabla como contrato antes de implementar. Listar devuelve un arreglo; obtener uno devuelve un objeto; crear responde 201; borrar termina con 204 sin cuerpo.

Una búsqueda sigue siendo una consulta de la colección. /contactos?buscar=ana no es otra clase de recurso: la consulta modifica cuáles elementos se devuelven. Conservamos los nombres del apunte, sin prefijo /api y con el parámetro buscar.

Apunte ↗

Los tres lugares responden preguntas diferentes. La ruta dice cuál contacto; la consulta modifica cómo se solicita una colección; el cuerpo lleva qué datos se envían para escribir.

13

Seguro e idempotente

Apunte ↗

En esta agenda, consultar no modifica los contactos. Repetir un PUT con el mismo contenido deja el mismo estado del recurso; repetir un POST exitoso crea otro contacto.

Observá el estado, no solo el código de respuesta. Después del primer DELETE el contacto ya no está: el siguiente puede responder 404 y, aun así, el estado sigue siendo «contacto ausente». Es una consecuencia de combinar la tabla con el manejador de borrado del propio apunte.

Un POST repetido crea 2 contactos. Un PUT repetido no.

14

Cada pedido trae todo lo necesario

Apunte ↗

Cada pedido tiene que identificar por sí mismo la operación. Para consultar el contacto 3, el cliente envía GET /contactos/3; no depende de que antes haya enviado «seleccioná el contacto 3».

Esta idea no elimina los datos persistidos. El mismo apunte incorpora después un archivo de contactos. La ausencia de memoria conversacional entre pedidos no significa que se borre la agenda después de responder. El dibujo con varias copias ilustra el principio; el proyecto no implementa ese despliegue.

15

Viaja una representación

Apunte ↗

Lo que cruza la conexión es la representación que el contrato eligió. En esta API, esa representación es JSON. El almacenamiento puede ser un arreglo o un archivo sin cambiar ese formato de intercambio.

El cliente recibe propiedades y valores, no una referencia al objeto que vive en el proceso de Node. Esa separación permite cambiar cómo se guarda sin obligar al consumidor a leer un archivo del servidor.

ExpressConstruir el primer CRUD

Reemplazamos el manejo manual de HTTP por rutas de Express. En esta etapa los contactos viven en un arreglo: primero aprendemos a responder, después a guardar.

16

Preparar el proyecto

Apunte ↗

La carpeta contiene el proyecto; npm init -y crea su configuración; type=module permite usar los import de los ejemplos; la instalación agrega Express como dependencia.

El apunte trabaja con Express 5 y más adelante muestra ^5.2.1 en package.json. La guía conserva esa referencia de versión, sin sustituirla por una supuesta versión más reciente.

Ver el ejemplo del apunteDiapositiva 16

17

Scripts para trabajar

Apunte ↗

Los scripts le ponen un nombre corto al comando de arranque. npm run dev usa node --watch para reiniciar al guardar; npm start ejecuta el archivo sin ese modo de observación.

Ambos apuntan a src/servidor.js. Creá ese archivo y su carpeta antes de ejecutar. Que el script se llame start no agrega validación, seguridad ni otras funciones a la aplicación: ejecuta exactamente el comando que está escrito.

18

El primer servidor con Express

Apunte ↗

express() crea la aplicación. app.get registra una función para un método y una ruta. Cuando llega el pedido correspondiente, res.send envía la respuesta.

Comparalo con el ejemplo de Node: ya no escribimos la condición req.method === "GET" ni el encabezado del texto a mano. El archivo termina abriendo el puerto con app.listen.

Ver el ejemplo del apunteDiapositiva 18

Cuando llegue un GET a /, ejecutá esta función. Hay uno por verbo: get, post, put, patch, delete.

19

Responder JSON

Apunte ↗

El arreglo se declara fuera del manejador, así que las solicitudes de este proceso consultan la misma colección en memoria. res.json(contactos) expresa que queremos devolverla como JSON.

Las líneas resaltadas son las agregadas respecto del servidor anterior. Los signos + del original son marcas didácticas: en los bloques copiables de esta guía se retiran, no son parte del JavaScript.

Ver el ejemplo del apunteDiapositiva 19
20

Elegir el código de estado

Apunte ↗

res.status(201) prepara el estado; .json(contacto) envía el cuerpo y termina la respuesta. La cadena reúne ambas acciones en una instrucción legible.

Para 204 usamos end() sin JSON. El otro límite importante es responder una sola vez: si una rama ya respondió, la función no debe continuar hacia otra respuesta.

Ver el ejemplo del apunteDiapositiva 20

status solo anota el código. La respuesta sale con json, send o end.

Cada pedido se responde una sola vez.

21

Parámetros de ruta

Apunte ↗

El segmento :id convierte una parte variable de la URL en req.params.id. En el ejemplo llega como texto y se convierte con Number para compararlo con los IDs numéricos del arreglo.

Si no se encuentra el contacto, return res.status(404)... responde y termina la función. Más adelante leerId agregará una validación explícita y distinguirá un ID inválido de uno válido pero inexistente.

Ver el ejemplo del apunteDiapositiva 21

Todo llega como texto: '2' === 2 es false.

El return evita responder 2 veces.

22

Parámetros de consulta

Apunte ↗

req.query contiene la consulta. El código verifica que buscar sea texto antes de llamar a toLowerCase; después filtra por coincidencia en el nombre.

El apunte muestra el caso de una clave repetida para advertir que no hay que suponer la forma del dato. En esta implementación, si buscar no es una cadena se devuelve la lista completa. La búsqueda no está implementada sobre teléfono ni email.

Ver el ejemplo del apunteDiapositiva 22

?buscar=a&buscar=b llega como arreglo. Nunca supongas la forma.

23

Leer el cuerpo

Apunte ↗

express.json() debe ejecutarse antes de las rutas que usan req.body. El POST asigna un ID, agrega el contacto y devuelve el recurso creado con 201 y Location.

Es una etapa deliberadamente incompleta. El orden { id: siguienteId++, ...req.body } permite que un id del cuerpo reemplace al asignado. La sección Validación resolverá este problema construyendo una lista explícita de campos aceptados; no uses este bloque como la versión final.

Ver el ejemplo del apunteDiapositiva 23

express.json() junta los trozos y deja el resultado en req.body. Va antes de las rutas.

Problema: si el cuerpo trae "id": 99, pisa el nuestro.

24

PUT reemplaza, PATCH modifica

Apunte ↗

Partimos del mismo contacto y enviamos el mismo cuerpo. El PUT reemplaza la representación editable: el teléfono que se omitió desaparece. El PATCH combina los cambios con los datos que ya estaban.

La diferencia no se adivina mirando el JSON enviado: la define el método y la implementación del contrato. En ambos casos el recurso sigue teniendo el identificador elegido en la ruta.

Ver el ejemplo del apunteDiapositiva 24
25

PUT y PATCH en código

Apunte ↗

PUT busca la posición y reemplaza el elemento del arreglo. PATCH encuentra el objeto y usa Object.assign para combinar sus propiedades con los cambios.

Estos son los manejadores previos a la validación. Conservamos el ejemplo para mostrar la diferencia entre reemplazo y modificación; el proyecto organizado utiliza validarContacto antes de llamar al repositorio y no entrega el cuerpo crudo a la persistencia.

Ver el ejemplo del apunteDiapositiva 25
26

Borrar responde 204

Apunte ↗

Primero se busca la posición. Si no existe, se devuelve 404; si existe, splice quita un elemento y la ruta responde 204.

El cliente no debe esperar un documento JSON de esta respuesta. En las pruebas mirá el código de estado y verificá con un GET posterior que el contacto ya no aparece.

204 significa que salió bien y no hay nada que devolver. Por eso end y no json.

MiddlewareOrdenar el recorrido
Un pedido no salta directamente a la base de datos. Recorre funciones en el orden en que se registraron: preparar, atender o continuar.
27

Apunte ↗
Leé la cadena de izquierda a derecha. El registro observa el pedido; el lector JSON prepara el cuerpo; una ruta atiende el recurso; la ruta inexistente responde si no hubo coincidencia.
El orden no es decorativo: cada función puede depender de lo que preparó una anterior. app.use registra pasos de ese recorrido.

28
Responder o pasar
Apunte ↗
Un middleware recibe next para pasar el control. Si ya atendió el pedido puede responder en lugar de continuar. El ejemplo separa claramente esas dos opciones.
Si una función no responde ni llama a next, la siguiente no se ejecuta y el cliente sigue esperando. En el simulador podés detener la cadena en ese punto y ver por qué no llega una respuesta.

29
Registrar cada pedido
Apunte ↗
El registro guarda el instante de entrada y se suscribe a finish para observar el final de la respuesta. Así puede mostrar el código efectivamente enviado y la duración calculada.
Después llama a next(): registrar un pedido no significa responderlo. Los tiempos del ejemplo son ilustrativos; este middleware mide los de cada ejecución real.

El orden importa
Apunte ↗
En el orden incorrecto, el POST se ejecuta antes de que exista un cuerpo JSON procesado. Colocar el parser después no prepara retroactivamente lo que ya leyó la ruta.
La organización propuesta por el apunte es: preparación, rutas, ruta inexistente y manejador de errores. Esta es la secuencia que recuperaremos al ensamblar app.js.

      Qué contiene el proyecto y qué no
      El ensamblado conserva las funciones finales del apunte. Retira las marcas de líneas nuevas, une fragmentos de una misma función y exporta los middlewares que app.js importa. No cambia nombres de rutas ni agrega autenticación, Drizzle o SQLite.
      La opción CORS se explica como paso adicional: el proyecto base no instala cors. La versión de Express declarada es la del apunte. El servidor se inicia con los comandos del material; no se afirma aquí que sea una configuración lista para publicar.
      Verificación: 54 comprobaciones de navegación, ejercicios y laboratorios en Chromium, con red deshabilitada; revisión en escritorio y a 390 px de ancho. Se usó la carga directa del contenido HTML porque este entorno bloquea navegar a archivos locales. También pasaron 21 comprobaciones independientes de los módulos de validación y repositorio con Node. Se confirmó que los 59 bloques originales están presentes y que la guía no carga recursos externos. No se ejecutó la integración completa con Express: el entorno no permitió descargar la dependencia desde npm. El proyecto se entrega como ensamblado del apunte, no como una API integralmente verificada.
