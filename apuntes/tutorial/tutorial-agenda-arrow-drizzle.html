Qué significa «dirección» en este proyecto

Domicilio es el texto de una ubicación postal. Una dirección es un medio de comunicación: teléfono, celular o email, con su valor. No son sinónimos. Usamos una tabla separada porque una persona puede tener varios medios de comunicación, incluso varios del mismo tipo.

server.mjs · sección 1 completa
export const contactos = sqliteTable('contactos', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  nombre: text('nombre').notNull(),
  apellido: text('apellido').notNull(),
  domicilio: text('domicilio').notNull().default(''),
});

export const direcciones = sqliteTable(
  'direcciones',
  {
    id: integer('id').primaryKey({ autoIncrement: true }),

    // Cada dirección pertenece a un contacto. Al borrar el padre, se borra la hija.
    contactoId: integer('contacto_id')
      .notNull()
      .references(() => contactos.id, { onDelete: 'cascade' }),

    tipo: text('tipo', { enum: TIPOS_DE_DIRECCION }).notNull(),
    valor: text('valor').notNull(),
  },
  (tabla) => [
    index('direcciones_contacto_idx').on(tabla.contactoId),
    check(
      'direcciones_tipo_check',
      sql`${tabla.tipo} in ('telefono', 'celular', 'email')`,
    ),
    check('direcciones_valor_check', sql`length(trim(${tabla.valor})) > 0`),
  ],
);

contactoId es la propiedad de JavaScript; contacto_id es la columna SQL. .references() describe la clave foránea y onDelete: 'cascade' expresa que las hijas se eliminan al borrar el padre. SQLite necesita tener activada la comprobación de claves foráneas en la conexión. [R3]

El enum de la declaración de texto no sustituye una restricción SQL. Por eso la tabla también declara un CHECK sobre los tipos admitidos. Una ayuda para el tipado y una regla aplicada por la base son controles distintos. [R4]

server.mjs · crearTablas · función completa
function crearTablas(db) {
  // Declarar tablas en Drizzle no las crea en SQLite. Este SQL solo inicializa
  // la demo. Los cambios futuros del esquema necesitan migraciones.
  db.transaction((transaccion) => {
    transaccion.run(sql`
      CREATE TABLE IF NOT EXISTS contactos (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        nombre TEXT NOT NULL,
        apellido TEXT NOT NULL,
        domicilio TEXT NOT NULL DEFAULT ''
      )
    `);

    transaccion.run(sql`
      CREATE TABLE IF NOT EXISTS direcciones (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        contacto_id INTEGER NOT NULL REFERENCES contactos(id) ON DELETE CASCADE,
        tipo TEXT NOT NULL CONSTRAINT direcciones_tipo_check
          CHECK (tipo IN ('telefono', 'celular', 'email')),
        valor TEXT NOT NULL CONSTRAINT direcciones_valor_check
          CHECK (length(trim(valor)) > 0)
      )
    `);

    transaccion.run(sql`
      CREATE INDEX IF NOT EXISTS direcciones_contacto_idx
      ON direcciones(contacto_id)
    `);
  });
}
Esquema declarado ≠ tablas creadas

Para mantener un único archivo de servidor, esta demo contiene la descripción de Drizzle y el SQL inicial. Deben estar alineados. CREATE TABLE IF NOT EXISTS crea lo que falta, pero no transforma una tabla existente cuando cambiás el modelo. Esa evolución corresponde a migraciones.

Comprobación

Ubicá dónde se garantiza que una dirección pertenece a un contacto. Después señalá dónde se valida el máximo de veinte. Son restricciones distintas, implementadas en lugares distintos.

04

Persistencia → API

Convertí dos tablas en un recurso.

Primero implementá la lectura del detalle. Es la operación que muestra con más claridad el cambio de representación: localizar al padre, obtener sus hijas y construir un objeto.

server.mjs · obtenerContacto · función completa
function obtenerContacto(db, id) {
  const contacto = db
    .select()
    .from(contactos)
    .where(eq(contactos.id, id))
    .get();

  if (!contacto) {
    return null;
  }

  const direccionesDelContacto = db
    .select({ tipo: direcciones.tipo, valor: direcciones.valor })
    .from(direcciones)
    .where(eq(direcciones.contactoId, id))
    .orderBy(asc(direcciones.id))
    .all();

  // Dos tablas SQL se presentan como un único objeto JSON anidado.
  return { ...contacto, direcciones: direccionesDelContacto };
}

eq(contactos.id, id) construye una comparación SQL. No es lo mismo que contactos.id === id, que compararía valores de JavaScript. Con el controlador síncrono elegido, .get() obtiene una fila y .all() un arreglo. .run() se utiliza cuando no necesitás filas de resultado. [R5]

Si el padre no existe, la función devuelve null. No decide una respuesta HTTP: esa traducción pertenece a la ruta. Así podés estudiar o reutilizar la persistencia sin objetos de Express.

05

Primera escritura

El contacto se guarda como una unidad.

Crear un contacto con dos direcciones requiere escribir en dos tablas. El orden importa: primero obtenés el identificador del padre; después lo colocás en cada fila hija. Y el conjunto debe confirmarse o revertirse de forma atómica. [R6]

server.mjs · crearContacto · función completa
function crearContacto(db, datos) {
  return db.transaction((transaccion) => {
    const contactoCreado = transaccion
      .insert(contactos)
      .values(extraerDatosPersonales(datos))
      .returning()
      .get();

    insertarDirecciones(transaccion, contactoCreado.id, datos.direcciones);

    return obtenerContacto(transaccion, contactoCreado.id);
  });
}

.returning().get() devuelve el contacto recién insertado, con su id. No lo inventes en el navegador ni uses «el mayor id más uno». La inserción devuelve el identificador que vas a relacionar. [R7]

server.mjs · extraerDatosPersonales · función completa
function extraerDatosPersonales(contacto) {
  return {
    nombre: contacto.nombre,
    apellido: contacto.apellido,
    domicilio: contacto.domicilio,
  };
}
server.mjs · insertarDirecciones · función completa
function insertarDirecciones(db, contactoId, listaDeDirecciones) {
  if (listaDeDirecciones.length === 0) {
    return;
  }

  const filas = listaDeDirecciones.map((direccion) => ({
    contactoId,
    tipo: direccion.tipo,
    valor: direccion.valor,
  }));

  db.insert(direcciones).values(filas).run();
}

La función compartida recibe db, pero puede trabajar con una transacción porque usa sus operaciones de consulta y escritura. En crearContacto se le pasa explícitamente transaccion: así la inserción de las hijas pertenece a la misma unidad.

Sin transacción

Puede quedar insertado el padre aunque falle una dirección. La operación de negocio quedó a medias.

Con transacción

Un fallo durante las escrituras revierte lo realizado dentro del bloque. No queda un contacto creado parcialmente.

Este bloque no es async

better-sqlite3 trabaja sincrónicamente. No hagas await fetch(...) dentro de su transacción. Prepará los datos externos antes de iniciarla y mantené la escritura breve. [R5]

Validá antes de escribir

server.mjs · validarContacto · función completa
function validarContacto(cuerpo) {
  if (!cuerpo || typeof cuerpo !== 'object' || Array.isArray(cuerpo)) {
    throw crearErrorHttp(400, 'Se esperaba un objeto JSON.');
  }

  if (!Array.isArray(cuerpo.direcciones)) {
    throw crearErrorHttp(400, 'direcciones debe ser un arreglo.');
  }

  if (cuerpo.direcciones.length > MAXIMO_DIRECCIONES) {
    throw crearErrorHttp(400, 'Se admiten hasta 20 direcciones por contacto.');
  }

  // Lista explícita de campos admitidos: los IDs recibidos no controlan la relación.
  return {
    nombre: validarTexto(cuerpo.nombre, 'nombre', 80),
    apellido: validarTexto(cuerpo.apellido, 'apellido', 80),
    domicilio: validarTexto(cuerpo.domicilio, 'domicilio', 200, false),
    direcciones: cuerpo.direcciones.map(validarDireccion),
  };
}

El servidor exige nombre y apellido de hasta ochenta caracteres; domicilio debe ser texto de hasta doscientos, aunque puede ser vacío. direcciones debe ser un arreglo —incluso cuando está vacío— y cada elemento necesita un tipo admitido y un valor. La comprobación de email es de formato básico, no verifica que exista esa dirección.

El objeto devuelto es una lista explícita de campos admitidos. Aunque alguien envíe id, contactoId o claveLocal, esos campos no deciden qué relación se escribe.

Actualizar: reemplazar la colección de direcciones

En esta API, PUT recibe el estado completo que debe tener el contacto. Actualiza el padre, elimina sus direcciones anteriores e inserta el arreglo recibido. Todo se ejecuta dentro de una transacción.

server.mjs · actualizarContacto · función completa
function actualizarContacto(db, id, datos) {
  return db.transaction((transaccion) => {
    const contactoActualizado = transaccion
      .update(contactos)
      .set(extraerDatosPersonales(datos))
      .where(eq(contactos.id, id))
      .returning()
      .get();

    if (!contactoActualizado) {
      return null;
    }

    // PUT reemplaza la colección completa. Un arreglo vacío quita todas las hijas.
    transaccion
      .delete(direcciones)
      .where(eq(direcciones.contactoId, id))
      .run();

    insertarDirecciones(transaccion, id, datos.direcciones);

    return obtenerContacto(transaccion, id);
  });
}

direcciones: [] significa «el contacto queda sin direcciones». Omitir la propiedad no significa lo mismo: la validación lo rechaza. Esta API no implementa un PATCH parcial.

Una decisión deliberada

No hay endpoints independientes para las direcciones. Se editan como parte del contacto. Sus IDs internos pueden cambiar en cada PUT, pero no forman parte del recurso público. Si más adelante una dirección necesita una identidad durable, historial o permisos propios, habrá que modificar este diseño.

Eliminar: el padre desaparece y la base resuelve las hijas

server.mjs · eliminarContacto · función completa
function eliminarContacto(db, id) {
  const contactoEliminado = db
    .delete(contactos)
    .where(eq(contactos.id, id))
    .returning({ id: contactos.id })
    .get();

  // La clave foránea resuelve el borrado de las direcciones; no hacemos otro DELETE.
  return contactoEliminado ?? null;
}

La ruta convierte un resultado inexistente en 404. Si se eliminó, termina con respuesta.status(204).end(). No envía {}: no hay cuerpo que interpretar.

function registrarRutasDeContactos(app, db) {
  app.get('/api/contactos', (solicitud, respuesta) => {
    const textoBusqueda = validarBusqueda(solicitud.query.q);
    const resultados = buscarContactos(db, textoBusqueda);

    respuesta.json(resultados);
  });

  app.get('/api/contactos/:id', (solicitud, respuesta) => {
    const id = validarId(solicitud.params.id);
    const contacto = obtenerContacto(db, id);

    exigirContactoExistente(contacto);
    respuesta.json(contacto);
  });

  app.post('/api/contactos', (solicitud, respuesta) => {
    const datos = validarContacto(solicitud.body);
    const contactoCreado = crearContacto(db, datos);

    respuesta.location(`/api/contactos/${contactoCreado.id}`);
    respuesta.status(201).json(contactoCreado);
  });

  app.put('/api/contactos/:id', (solicitud, respuesta) => {
    const id = validarId(solicitud.params.id);
    const datos = validarContacto(solicitud.body);
    const contactoActualizado = actualizarContacto(db, id, datos);

    exigirContactoExistente(contactoActualizado);
    respuesta.json(contactoActualizado);
  });

  app.delete('/api/contactos/:id', (solicitud, respuesta) => {
    const id = validarId(solicitud.params.id);
    const contactoEliminado = eliminarContacto(db, id);

    exigirContactoExistente(contactoEliminado);
    respuesta.status(204).end();
  });
}

El patrón se repite de forma visible: validar entrada → llamar a persistencia → interpretar resultado → responder. Las consultas no están mezcladas dentro de cada manejador.

server.mjs · responderError · función completa
function responderError(error, solicitud, respuesta, siguiente) {
  if (respuesta.headersSent) {
    siguiente(error);
    return;
  }

  let status = error.status || 500;
  let mensaje = error.message;

  if (error.type === 'entity.parse.failed') {
    status = 400;
    mensaje = 'JSON inválido.';
  } else if (status === 413) {
    mensaje = 'El cuerpo supera 32 KB.';
  } else if (status >= 500) {
    console.error(error);
    mensaje = 'Error interno del servidor.';
  }

  respuesta.status(status).json({ error: mensaje });
}

index.html · codigo-agenda · solicitarJson · función completa
async function solicitarJson(ruta, { metodo = 'GET', cuerpo, registrar = true } = {}) {
  const opciones = {
    method: metodo,
    headers: { Accept: 'application/json' },
    cache: 'no-store',
  };

  if (cuerpo !== undefined) {
    opciones.headers['Content-Type'] = 'application/json';
    opciones.body = JSON.stringify(cuerpo);
  }

  let respuesta;

  try {
    respuesta = await fetch(URL_API + ruta, opciones);
  } catch {
    throw new Error('No se pudo conectar con la API. Comprobá que el servidor esté iniciado.');
  }

  const texto = await respuesta.text();
  let datos = null;

  try {
    // DELETE devuelve 204 y no contiene un documento JSON.
    if (texto !== '') {
      datos = JSON.parse(texto);
    }
  } catch {
    throw new Error('La API no devolvió JSON. Revisá la URL del servidor.');
  }

  if (registrar) {
    registrarOperacion(metodo, ruta, cuerpo, respuesta.status, datos);
  }

  if (!respuesta.ok) {
    throw new Error(datos?.error || `Error HTTP ${respuesta.status}`);
  }

  return datos;
}

JSON.stringify convierte el objeto en el texto enviado. Content-Type describe ese cuerpo; Accept comunica qué representación espera el cliente. fetch no rechaza automáticamente una respuesta 400 o 404: hay que examinar respuesta.ok. Un error de red y un error HTTP son situaciones diferentes. [R10]

El código lee primero texto para contemplar el 204 vacío. Si el servidor devuelve HTML en vez de JSON —por ejemplo, una URL equivocada— muestra un mensaje específico. La traza se registra antes de lanzar un error HTTP, para poder estudiarlo.

      return;

      registrarOperacion('GET', `/contactos?q=${consulta}`, null, 200, contactosEncontrados);

      estado.error = error.message;
    }
  } finally {
    if (numeroBusqueda === ultimaBusqueda) {
      estado.buscando = false;

  }

server.mjs · crearFiltroDeBusqueda · función completa
function crearFiltroDeBusqueda(db, textoBusqueda) {
  const texto = normalizarTexto(textoBusqueda).trim();

  if (texto === '') {
    return undefined;
  }

  const datosPersonales = sql`
    ${contactos.nombre} || ' ' || ${contactos.apellido} || ' ' || ${contactos.domicilio}
  `;

  const coincideElContacto = contieneTexto(datosPersonales, texto);
  const coincideUnaDireccion = exists(
    db
      .select({ coincidencia: sql`1` })
      .from(direcciones)
      .where(
        and(
          eq(direcciones.contactoId, contactos.id),
          contieneTexto(direcciones.valor, texto),
        ),
      ),
  );

  // EXISTS evita que el filtro reduzca la cantidad de direcciones del resumen.
  return or(coincideElContacto, coincideUnaDireccion);
}
server.mjs · contieneTexto · función completa
function contieneTexto(columna, texto) {
  // Parámetro SQL, no concatenación. % y _ se buscan como caracteres literales.
  return sql`instr(normalizar(${columna}), ${texto}) > 0`;
}

El texto se normaliza en ambos lados de la comparación mediante la función registrada en SQLite. En esta implementación «garcia» encuentra «García». Se usa instr, no un patrón LIKE: los símbolos % y _ se buscan literalmente.

function buscarContactos(db, textoBusqueda) {
  const filtro = crearFiltroDeBusqueda(db, textoBusqueda);

  return db
    .select({
      id: contactos.id,
      nombre: contactos.nombre,
      apellido: contactos.apellido,
      domicilio: contactos.domicilio,
      cantidadDirecciones: count(direcciones.id),
    })
    .from(contactos)
    .leftJoin(direcciones, eq(direcciones.contactoId, contactos.id))
    .where(filtro)
    .groupBy(contactos.id)
    .orderBy(
      sql`normalizar(${contactos.apellido})`,
      sql`normalizar(${contactos.nombre})`,
      asc(contactos.id),
    )
    .all();
}

async function iniciarAgenda() {
  const contenedor = document.querySelector('#app');
  contenedor.replaceChildren();
  vistaAplicacion()(contenedor);

  if (location.protocol === 'file:') {
    estado.error = 'No abras el HTML con doble clic. Ejecutá npm start y abrí http://127.0.0.1:3000.';
    return;
  }

  await cargarContactos();

  if (estado.contactos.length > 0 && estado.contactoEnEdicion === null) {
    await seleccionarContacto(estado.contactos[0].id);
  }
}

vistaAplicacion()(contenedor) primero produce la plantilla y después la monta. Solo entonces se solicita el listado inicial y, si hay resultados, se selecciona el primero.

    Un ejercicio para extender el modelo
    
  
    Agregá un campo notas al contacto. Debe ser opcional en la experiencia del formulario, guardarse como texto y volver en el GET. Antes de tocar código, recorré el trayecto e identificá todos los lugares que deben cambiar.
    
  
    Ver una guía de solución
    Modificá la declaración Drizzle y el esquema físico mediante una migración si ya hay datos. Agregá el campo a la validación, a extraerDatosPersonales, al contrato esperado y a las pruebas. En el frontend, incorporalo al objeto vacío, a extraerDatosEditables y a la vista del detalle. Verificá creación, edición, Cancelar y persistencia entre reinicios.
    No alcanza con dibujar un input: si la función que construye el cuerpo no envía el campo, nunca cruza la API. Tampoco alcanza con enviarlo: si el servidor no lo admite, la lista explícita de campos lo elimina.
    
  
    Un segundo ejercicio: identidad de las direcciones
    
  
    Imaginá que otra entidad necesita referirse a una dirección concreta. Explicá por qué el reemplazo «borrar e insertar» de PUT deja de ser una buena simplificación y qué información necesitaría el contrato para conservar IDs.
    
  
    Ver una guía de solución
    Las direcciones necesitarían una identidad pública estable. La actualización tendría que diferenciar filas nuevas, modificadas y eliminadas, verificar que cada ID pertenece al contacto y aplicar esas diferencias dentro de una transacción. Un endpoint por hija podría ser una alternativa, pero no es obligatorio: también podés conservar una edición anidada con IDs.
    
  
    Límites que no hay que esconder
    
  
    
    
    Sin autenticación
    Es una demo local. CORS no determina quién puede leer o modificar una persona. No publiques datos personales con esta configuración.
    
    
    Sin control de versiones
    Dos clientes pueden editar el mismo contacto. Una escritura posterior puede pisar la anterior; esta API no detecta conflictos de edición.
    
    
    Sin migraciones evolutivas
    El SQL inicial crea tablas nuevas. Cambiar una columna en el código no actualiza automáticamente una base existente.
    
    
    Búsqueda sin paginar
    El listado final devuelve todas las coincidencias. No es una estrategia de escala para una agenda masiva.
    
    
    Escrituras síncronas
    El controlador elegido simplifica el ejemplo, pero operaciones largas ocupan el hilo donde se ejecutan. No agregues trabajo remoto a una transacción.
    
    
    Hijas sin identidad pública
    El reemplazo de direcciones es simple porque nadie externo depende de sus IDs. Esa condición puede dejar de cumplirse.
    
  
    
  
    Criterio de dominio
    Entendiste la aplicación cuando podés agregar un dato, seguirlo desde el formulario hasta una fila y predecir qué pasará si falla cada paso. Recordar nombres de métodos ayuda; ubicar responsabilidades es lo que permite modificar el sistema.
