5. Para trabajar correctamente con Unicode moderno conviene usar `codePointAt()`, iteradores (`for...of`, `[...s]`) y normalización cuando corresponda.

6. Para **orden alfabético humano**, no alcanza con `<`, `>` o `sort()`; conviene `localeCompare()` o `Intl.Collator`.

Ahora podemos profundizar en las consecuencias prácticas.

# 27. Recorrer correctamente un `string`

La forma aparentemente obvia es:

```js
const texto = "A😀B";

for (let i = 0; i < texto.length; i++) {
    console.log(texto[i]);
}
```

Pero `length` e índices trabajan con unidades UTF-16. Por eso el emoji queda dividido.

Conceptualmente obtenemos:

```text
A
<primera mitad de 😀>
<segunda mitad de 😀>
B
```

En cambio:

```js
for (const caracter of texto) {
    console.log(caracter);
}
```

produce:

```text
A
😀
B
```

Lo mismo ocurre con:

```js
[..."A😀B"]
// ["A", "😀", "B"]
```

### Regla práctica

Para procesamiento Unicode:

```js
for (const c of texto) {
    // ...
}
```

suele ser preferible a:

```js
for (let i = 0; i < texto.length; i++) {
    const c = texto[i];
}
```

---

# 28. Code units, code points y grafemas

Hay que distinguir **tres conceptos**.

Supongamos:

```js
const s = "😀";
```

Tenemos:

```text
Grafema visible:      😀
Code point:           U+1F600
Code units UTF-16:    D83D DE00
```

Entonces:

```js
s.length
// 2

[...s].length
// 1
```

Pero todavía queda una dificultad.

Consideremos:

```js
const s = "a\u0301";
```

Visualmente:

```text
á
```

Sin embargo:

```js
[...s]
// ["a", "́"]
```

Hay **dos code points**, aunque una persona ve **una letra**.

Así que tenemos:

```text
code unit   ≠   code point   ≠   carácter visual
```

El término técnico para este último es **grapheme cluster** o *grupo de grafemas*.

---

# 29. Los emoji hacen visible el problema

Consideremos:

```text
👨‍👩‍👧‍👦
```

Visualmente es un solo emoji: una familia.

Pero está construido combinando varios code points.

Por eso:

```js
const familia = "👨‍👩‍👧‍👦";

familia.length
// mucho mayor que 1

[...familia].length
// también mayor que 1
```

Aunque el usuario ve:

```text
👨‍👩‍👧‍👦
```

como una sola unidad visual.

Por eso cortar strings arbitrariamente puede generar resultados bastante desagradables.

---

# 30. `Intl.Segmenter`

JavaScript moderno puede segmentar texto según reglas lingüísticas.

```js
const segmenter =
    new Intl.Segmenter("es", {
        granularity: "grapheme"
    });

const texto = "Hola 👨‍👩‍👧‍👦";

const partes =
    [...segmenter.segment(texto)];

console.log(partes);
```

Esto permite trabajar mucho mejor con lo que el usuario percibe como caracteres.

Es una distinción conceptual importante:

```text
"😀".length
       ↓
unidades UTF-16

[..."😀"].length
       ↓
code points

Intl.Segmenter
       ↓
grafemas percibidos
```

# 31. Concatenación

La operación fundamental entre strings es unirlos:

```js
const nombre = "Ana";

const mensaje =
    "Hola " + nombre;
```

El operador `+` está sobrecargado.

Puede significar suma:

```js
2 + 3
// 5
```

o concatenación:

```js
"2" + "3"
// "23"
```

Esto nos lleva directamente a una particularidad importante de JavaScript.

---

# 32. Conversión implícita a `string`

JavaScript tiene coerción automática de tipos.

```js
"Edad: " + 25
// "Edad: 25"
```

El número `25` fue convertido implícitamente en:

```js
"25"
```

Esto puede provocar resultados sorprendentes:

```js
1 + 2
// 3
```

pero:

```js
"1" + 2
// "12"
```

y:

```js
1 + "2"
// "12"
```

Una vez que `+` actúa como concatenación, los operandos correspondientes se convierten a texto.

Por eso:

```js
1 + 2 + "3"
```

se evalúa de izquierda a derecha:

```text
1 + 2
  ↓
  3

3 + "3"
  ↓
"33"
```

Resultado:

```js
"33"
```

Mientras:

```js
"1" + 2 + 3
```

produce:

```text
"1" + 2
   ↓
 "12"

"12" + 3
   ↓
 "123"
```

# 33. Conversión explícita

Podemos convertir explícitamente a string:

```js
String(123)
// "123"

String(true)
// "true"

String(null)
// "null"

String(undefined)
// "undefined"
```

También:

```js
const n = 123;

n.toString();
// "123"
```

Hay una diferencia práctica:

```js
String(null)
// "null"
```

pero:

```js
null.toString()
// TypeError
```

Por eso `String(valor)` es una conversión general más segura.

---

# 34. Conversión de números con distintas bases

`toString()` tiene una capacidad particularmente interesante:

```js
const n = 42;

n.toString(10)
// "42"

n.toString(2)
// "101010"

n.toString(16)
// "2a"
```

Es decir:

```text
número
   ↓
representación textual
```

Por ejemplo:

```js
255..toString(16)
// "ff"
```

Esto es importante conceptualmente: `"101010"` no es un número binario almacenado misteriosamente de otra manera.

Es simplemente un **string que representa un número en base 2**.

---

# 35. Comparación lexicográfica

Volvamos a:

```js
"casa" < "cosa"
// true
```

La idea es comparar posición por posición:

```text
casa
cosa
│
c = c
```

Seguimos:

```text
casa
cosa
 │
 a < o
```

Y ya tenemos el resultado.

Esto es parecido a buscar palabras en un diccionario.

Pero la comparación básica de JavaScript utiliza valores UTF-16, no reglas lingüísticas de un idioma.

---

# 36. Una consecuencia muy importante

```js
"10" < "2"
// true
```

Esto suele sorprender al principio.

Pero estamos comparando **strings**, no números.

La primera posición es:

```text
"10"
"2"

'1' < '2'
```

Por lo tanto:

```js
"10" < "2"
// true
```

En cambio:

```js
10 < 2
// false
```

Es una diferencia fundamental entre:

```text
valor numérico
```

y:

```text
representación textual del valor
```

---

# 37. El problema clásico al ordenar números almacenados como strings

Consideremos:

```js
const valores = [
    "1",
    "2",
    "10",
    "20",
    "3"
];

valores.sort();
```

Obtendremos algo parecido a:

```js
[
    "1",
    "10",
    "2",
    "20",
    "3"
]
```

Perfectamente correcto **como texto**.

Incorrecto si pretendíamos interpretar esos strings como números.

Entonces:

```js
valores.sort(
    (a, b) => Number(a) - Number(b)
);
```

produce el orden numérico esperado.

---

# 38. Comparación lingüística

Para personas queremos algo diferente.

Supongamos:

```js
const palabras = [
    "nube",
    "Ñandú",
    "árbol",
    "zapato",
    "avión"
];
```

No queremos razonar en términos de posiciones Unicode.

Queremos decir:

> "ordená esto como lo ordenaría alguien que habla español".

Ahí usamos:

```js
palabras.sort(
    (a, b) => a.localeCompare(b, "es")
);
```

O mejor, si vamos a comparar muchas veces:

```js
const español =
    new Intl.Collator("es");

palabras.sort(español.compare);
```

`Intl.Collator` encapsula las reglas de **collation**: ordenamiento lingüístico.

---

# 39. Comparaciones ignorando mayúsculas y acentos

Para determinadas búsquedas podemos querer considerar equivalentes:

```text
ÁRBOL
árbol
Arbol
arbol
```

Podemos construir:

```js
const comparador =
    new Intl.Collator("es", {
        sensitivity: "base"
    });
```

Y comparar:

```js
comparador.compare("árbol", "ARBOL")
// 0
```

El `0` significa:

> para los criterios de este comparador son equivalentes.

Esto suele ser mucho más correcto que hacer manualmente:

```js
a.toLowerCase() === b.toLowerCase()
```

porque el tratamiento lingüístico de mayúsculas, acentos y alfabetos es más complejo de lo que parece.

# 40. Template literals: hay más que interpolación

Habíamos visto:

```js
const nombre = "Ana";

const mensaje =
    `Hola ${nombre}`;
```

Pero `${}` acepta expresiones completas:

```js
const precio = 100;
const cantidad = 3;

const mensaje =
    `Total: $${precio * cantidad}`;
```

Resultado:

```text
Total: $300
```

También:

```js
`${usuario.activo ? "Activo" : "Inactivo"}`
```

o:

```js
`${productos.length} productos`
```

La idea fundamental es:

```text
texto estático + expresión JS + texto estático
```

---

# 41. Tagged templates

Los template literals tienen una capacidad bastante más profunda:

```js
html`<h1>${titulo}</h1>`
```

o:

```js
sql`
    SELECT *
    FROM usuarios
    WHERE id = ${id}
`
```

Aquí `html` y `sql` pueden ser **funciones**.

Por ejemplo:

```js
function mostrar(partes, valor) {
    console.log(partes);
    console.log(valor);
}

const nombre = "Ana";

mostrar`Hola ${nombre}!`;
```

La función recibe separadamente:

```text
["Hola ", "!"]

y

"Ana"
```

Esto permite procesar la interpolación antes de construir el resultado.

Es la base conceptual de APIs como:

```js
html`...`
sql`...`
css`...`
```

y permite, por ejemplo, escapar valores, construir consultas parametrizadas o generar estructuras.

# 42. `String.raw`

Normalmente:

```js
console.log("A\nB");
```

interpreta `\n` como salto de línea.

Con:

```js
String.raw`A\nB`
```

obtenemos literalmente:

```text
A\nB
```

Puede resultar útil trabajando con expresiones regulares, rutas y otros textos donde las barras invertidas tienen significado.

# 43. Strings y expresiones regulares

Los strings suelen procesarse mediante expresiones regulares.

Por ejemplo:

```js
const texto = "Juan tiene 57 años";

texto.match(/\d+/);
// ["57"]
```

Reemplazar:

```js
"hola    mundo".replace(/\s+/g, " ");
// "hola mundo"
```

Separar:

```js
"uno, dos; tres".split(/[,;]/);
// ["uno", " dos", " tres"]
```

Y Unicode vuelve a aparecer aquí.

Las expresiones regulares modernas tienen el flag:

```js
/u
```

para trabajar con semántica Unicode:

```js
/😀/u
```

y propiedades Unicode:

```js
/\p{Letter}/u
```

Por ejemplo:

```js
"ñ".match(/\p{Letter}/u);
// ["ñ"]
```

Esto evita pensar que "letra" significa simplemente `[A-Za-z]`, que en un mundo Unicode es una definición bastante pobre de letra.

# 44. Un experimento que resume casi todo

Este pequeño programa merece ser ejecutado:

```js
const s = "A😀á";

console.log("Texto:", s);

console.log(
    "length:",
    s.length
);

console.log(
    "Code points:",
    [...s]
);

console.log(
    "Unicode:",
    [...s].map(
        c =>
            "U+" +
            c.codePointAt(0)
             .toString(16)
             .toUpperCase()
    )
);

console.log(
    "UTF-8:",
    [...new TextEncoder().encode(s)]
);
```

Estamos observando **el mismo texto desde distintas capas**:

```text
              "A😀á"
                 │
        ┌────────┼─────────┐
        │        │         │
        ▼        ▼         ▼
     Unicode   UTF-16    UTF-8
       │          │        │
 code points   length    bytes
```

Y esa es probablemente la idea más importante de todo el tema:

> **Un string no es "una lista de bytes".**

El texto tiene una representación abstracta mediante Unicode; JavaScript expone sus strings históricamente como unidades UTF-16, mientras que UTF-8 aparece normalmente cuando necesitamos convertir ese texto en bytes para almacenarlo o transmitirlo.

Entendiendo esa separación, dejan de parecer misteriosos `"😀".length === 2`, `TextEncoder`, `codePointAt()`, los problemas con acentos y buena parte de las rarezas del procesamiento de texto en JavaScript.
