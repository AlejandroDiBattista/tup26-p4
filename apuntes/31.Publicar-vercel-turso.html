Publicar en Vercel y Turso desde el navegador

Un camino de deploy sin terminal, pensado para quienes trabajan en Windows. Todo se hace desde las páginas de GitHub, Vercel y Turso; el build de Vercel crea las tablas y carga los datos de prueba solo.

La idea

En el camino con terminal, vos corrés db:migrate y db:seed contra Turso desde tu máquina, pasando el token. Eso es lo que se complica en Windows. Acá esos dos pasos los hace Vercel en cada deploy, antes de construir la app:

git pushdesde VS Code
→
Migracionescrea o actualiza las tablas en Turso
→
Datos de pruebasolo si la base está vacía
→
next buildy la URL pública

Los secretos (el token de Turso y el SESSION_SECRET) se cargan una sola vez en el panel de Vercel y nunca pasan por tu terminal ni por el chat de un agente.

Preparar el proyecto (una sola vez)

El proyecto necesita un script que prepare la base antes del build. Hace cuatro cosas:

  • Acepta tanto DATABASE_URL / DATABASE_AUTH_TOKEN como TURSO_DATABASE_URL / TURSO_AUTH_TOKEN, que son las que crea la integración de Turso.
  • Aplica las migraciones de drizzle/ con el migrador de Drizzle.
  • Si la base no tiene usuarios, carga los datos de prueba con los servicios de la app.
  • En Vercel solo actúa en Production y corta el build con un mensaje claro si falta una variable.

En package.json, el build queda así:

package.json
"build": "tsx src/db/deploy.ts && next build",
"db:deploy": "tsx src/db/deploy.ts"

El núcleo de src/db/deploy.ts:

src/db/deploy.ts (resumido)
import "dotenv/config";
import { migrate } from "drizzle-orm/libsql/migrator";
import { db } from "./index";
import { baseVacia, cargarDatosDePrueba } from "./datos-prueba";

async function main() {
  // En Vercel, los deploys de preview no tocan la base
  if (process.env.VERCEL && process.env.VERCEL_ENV !== "production") return;
  await migrate(db, { migrationsFolder: "drizzle" });
  if (await baseVacia()) await cargarDatosDePrueba();
}

main().then(() => process.exit(0), (e) => { console.error(e); process.exit(1); });

La versión completa, con los mensajes de error y la recarga con SEED_RESET, está en el proyecto de referencia. Si tu proyecto es distinto, pedíselo a tu agente:

prompt para Claude Code, Codex u OpenCode
Quiero publicar este proyecto en Vercel sin usar la terminal. Agregá un script src/db/deploy.ts que se ejecute antes de next build (cambiá el script build a "tsx src/db/deploy.ts && next build") y que:

1. Lea la conexión de DATABASE_URL o TURSO_DATABASE_URL, y el token de DATABASE_AUTH_TOKEN o TURSO_AUTH_TOKEN (usá el mismo criterio en src/db/index.ts y drizzle.config.ts).
2. En Vercel, no haga nada si VERCEL_ENV no es "production".
3. En producción, corte el build con un mensaje claro si falta la base o si SESSION_SECRET falta, tiene menos de 32 caracteres o es el de .env.example.
4. Aplique las migraciones con migrate() de drizzle-orm/libsql/migrator sobre la carpeta drizzle.
5. Si la base no tiene usuarios, cargue los datos de prueba reutilizando la lógica de mi seed (separala en una función exportada para no duplicarla).
6. Con SEED_RESET=valor, recargue los datos una sola vez por valor, guardando una marca en la base.

Probalo con la base local: base nueva, segunda ejecución y VERCEL=1 VERCEL_ENV=preview. No toques .env ni me pidas secretos. Mostrame el diff antes de commitear.
Los alumnos que ya tienen el proyecto funcionando en local solo agregan este script. El resto del deploy no requiere cambios en el código.

Antes de empezar

  • Cuentas gratuitas en GitHub, Vercel y Turso. Con la cuenta de GitHub podés entrar a las otras dos.
  • Git y VS Code instalados. En Windows: git-scm.com y code.visualstudio.com.
  • El proyecto funcionando en local, con commits.

No hace falta instalar las CLIs de Turso ni de Vercel, ni WSL.

Los menús de Vercel y Turso cambian de nombre de vez en cuando. Si no encontrás exactamente el botón que dice la guía, buscá uno equivalente en la misma pantalla.
Paso 1

Subir el repositorio a GitHub

  • En VS Code abrí la carpeta del proyecto y andá a Source Control (Ctrl+Shift+G).
  • Si nunca lo subiste: Publish Branch → elegí private repository. Si ya existe en GitHub: Sync Changes.
  • Abrí el repositorio en GitHub y fijate que no estén .env ni local.db.
Si ves .env en GitHub, frená acá. Borralo del repositorio, agregalo a .gitignore y cambiá cualquier secreto que haya tenido: lo que se subió una vez queda en el historial.
Paso 2

Crear el proyecto en Vercel

  • En vercel.com/new, conectá tu cuenta de GitHub e importá el repositorio.
  • Vercel detecta Next.js y pnpm. No cambies nada y tocá Deploy.
  • Este primer build va a fallar con «Falta la base de datos». Es lo esperado: todavía no hay base.
Paso 3

Crear la base en Turso

Elegí una de las dos opciones.

  • En el proyecto de Vercel, andá a Storage (o Integrations → Marketplace) y elegí Turso.
  • Creá una base nueva y conectala a este proyecto, al menos para el entorno Production.
  • La integración carga sola las variables TURSO_DATABASE_URL y TURSO_AUTH_TOKEN. Comprobalo en Settings → Environment Variables.

No copiás ningún token: es la opción más simple.

  • En app.turso.tech creá una base llamada mostrador.
  • Copiá su URL, que empieza con libsql://, y generá un token para esa base.
  • En Vercel → Settings → Environment Variables cargá DATABASE_URL con la URL y DATABASE_AUTH_TOKEN con el token, marcando solo Production.

El token se pega directamente de la página de Turso a la de Vercel; no lo guardes en archivos ni lo pegues en un chat.

Paso 4

Cargar el SESSION_SECRET

Es la clave con la que la app firma las cookies de sesión: un texto al azar de 32 caracteres o más. Para generarlo sin terminal, abrí la consola del navegador (F12 → Console) y escribí:

consola del navegador
crypto.randomUUID() + crypto.randomUUID()

Copiá el resultado sin las comillas y cargalo en Vercel como SESSION_SECRET, solo en Production.

No uses el valor de .env.example. Está en el repositorio, así que cualquiera podría firmar una sesión válida. El build se corta si lo detecta.
Paso 5

Publicar

Las variables se leen en cada deploy, así que hay que volver a publicar: Deployments → el último → menú ⋯ → Redeploy. En el log del build tenés que ver, antes de la compilación de Next.js:

log del build en Vercel
Aplicando migraciones…
Base vacía: se cargan los datos de prueba…
  …
  Invariantes: stock = suma de movimientos ✔ · sin saldos a favor ✔

La primera vez la carga de datos tarda un poco más, porque crea unas 70 facturas en Turso. En los deploys siguientes vas a ver «La base ya tiene datos: no se cargan datos de prueba».

Desde ahora, cada Sync Changes en VS Code publica una versión nueva.

Paso 6

Probar en producción

Abrí la URL que muestra Vercel (https://<proyecto>.vercel.app), entrá con los usuarios de prueba del README y recorré el guion de la defensa, verificando stock y saldo después de cada paso:

  • Venta a consumidor final con efectivo.
  • Venta a un cliente nuevo, dado de alta en el momento, en cuenta corriente.
  • Pago de ese cliente, con su recibo.
  • Anulación de una factura con el usuario administrador.

Por último, completá la URL pública y los integrantes en el README y sincronizá.

Recargar los datos antes de la defensa

Las facturas de prueba se fechan en los 30 días anteriores a la carga, así que con el tiempo el tablero se queda sin ventas recientes. Para recargarlas:

  • En Settings → Environment Variables agregá SEED_RESET con un valor nuevo, por ejemplo defensa-1.
  • Hacé Redeploy. El log dice «SEED_RESET=defensa-1: se vuelven a cargar los datos de prueba…».

Se recarga una sola vez por valor: aunque la variable quede cargada, los deploys siguientes no borran nada. Para recargar de nuevo, cambiá el valor a defensa-2.

Recargar borra todo lo que hayas cargado en producción. Ventas, clientes y usuarios nuevos se pierden y vuelven los datos de prueba.

Problemas frecuentes

Todo se diagnostica desde el log: Deployments → el deploy → Build Logs. Si usás un agente, podés pegarle el log; antes revisá que no tenga ningún token.

Lista para la entrega

  1. El repositorio de GitHub tiene el código y el historial de commits, sin .env ni local.db.
  2. La URL pública de Vercel abre /login y se puede entrar con los usuarios de prueba.
  3. El log del último deploy muestra las migraciones aplicadas y la app usa la base de Turso.
  4. El README tiene integrantes, URL pública, instalación, variables (.env.example), usuarios por rol, requerimientos por código y arquitectura.
  5. Podés explicar qué hace deploy.ts y por qué no toca la base en los previews.
