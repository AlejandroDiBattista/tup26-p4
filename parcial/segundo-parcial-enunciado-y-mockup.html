Programación web / Segundo parcial

Sistema de ventas y gestión comercial

Enunciado y prototipo de referencia para el desarrollo de una aplicación web integral.

Prototipo de referencia. Las pantallas de este archivo ilustran una posible organización y algunos flujos del sistema. Usan datos ficticios y no guardan información. Podés tomarlas como punto de partida o proponer otro diseño: lo obligatorio es cumplir los requisitos del enunciado.

Objetivo

Desarrollar una aplicación web que permita gestionar las ventas de un comercio, su catálogo de productos, las existencias y las cuentas corrientes de sus clientes.

El sistema debe integrar estas funciones: al realizar una venta, debe registrar un comprobante, descontar las existencias correspondientes y, si la venta se realiza en cuenta corriente, registrar la deuda del cliente.

La aplicación debe contar con una interfaz clara y profesional, una base de datos persistente y una versión publicada en internet.

Funcionalidades requeridas

1. Ventas y facturación

El sistema debe permitir registrar una venta con los siguientes datos:

  • Cliente: consumidor final o un cliente registrado. Si la persona no está registrada, debe poder darse de alta durante la venta y seleccionarse sin perder los datos ya cargados.
  • Productos: uno o más productos del catálogo, indicando la cantidad de cada uno.
  • Detalle: descripción, cantidad, precio unitario y subtotal de cada producto.
  • Total: suma de los subtotales.
  • Forma de pago: contado, tarjeta o cuenta corriente.

Mientras se prepara la venta, se deben poder agregar y quitar productos y modificar sus cantidades. Los subtotales y el total se actualizan con esos cambios.

Antes de confirmar la venta, el sistema debe verificar que haya existencias suficientes de todos los productos. Si falta stock, debe informar el problema y permitir corregir la venta.

Al confirmar una venta, el sistema debe:

  1. Registrar un comprobante con un número único, fecha, cliente, detalle, total y forma de pago.
  2. Descontar del stock las cantidades vendidas.
  3. Si la venta es en cuenta corriente, registrar la deuda en la cuenta del cliente.

La venta en cuenta corriente solo está disponible para clientes registrados. La operación debe ser completa: si la venta no puede confirmarse, no deben quedar descontadas las existencias ni generada la deuda.

El sistema debe permitir consultar el listado de ventas y ver el detalle de cada comprobante. Los datos de una venta registrada deben conservarse tal como eran en ese momento, aunque luego se modifiquen los precios, los nombres de los productos o los datos del cliente.

Alcance de la facturación: el comprobante es una representación interna para este ejercicio. No se requiere integración con ARCA ni emisión de comprobantes fiscales. El pago con tarjeta se registra de manera simulada: no se deben solicitar ni almacenar números de tarjeta.

2. Productos y stock

El sistema debe permitir:

  • Dar de alta, consultar y modificar productos.
  • Buscar productos por nombre o código.
  • Registrar para cada producto, como mínimo, código, nombre, precio de venta, stock actual y estado activo o inactivo.
  • Registrar entradas y salidas manuales de stock, indicando cantidad y motivo.
  • Consultar los movimientos de stock, distinguiendo los ajustes manuales de las ventas.

El código de producto debe ser único, el precio debe ser positivo y las cantidades se manejan en unidades enteras. El stock inicial se registra como una entrada, si es mayor que cero.

Las cantidades de los movimientos deben ser positivas y el stock no puede quedar negativo. Un producto inactivo no debe poder agregarse a nuevas ventas, pero debe seguir apareciendo en los comprobantes anteriores.

3. Clientes y cuentas corrientes

El sistema debe permitir dar de alta, consultar y modificar clientes, así como buscarlos por nombre o documento.

Para cada cliente se deben registrar, como mínimo, nombre y apellido o razón social, documento o identificación y algún dato de contacto.

Cada cliente debe tener una cuenta corriente en la que se pueda:

  • Consultar el saldo adeudado.
  • Ver las ventas realizadas en cuenta corriente.
  • Registrar pagos, indicando fecha, importe y una observación opcional.
  • Consultar el historial de movimientos.

El saldo se calcula como la suma de las ventas en cuenta corriente menos los pagos registrados. No se deben admitir pagos mayores que el saldo adeudado. Las ventas pagadas de contado o con tarjeta no generan deuda.

4. Usuarios y acceso

La aplicación debe requerir inicio de sesión para acceder a sus funciones y permitir cerrar la sesión.

Debe existir un usuario administrador que pueda crear usuarios para operar el sistema. Como mínimo, cada usuario tendrá nombre, nombre de acceso o correo, contraseña y estado activo o inactivo. Un usuario inactivo no podrá iniciar sesión.

La administración de usuarios (consulta, alta, edición y activación o desactivación) está reservada al administrador. Los demás usuarios pueden operar ventas, productos, clientes, stock y pagos. Los permisos deben verificarse en el servidor.

Las contraseñas no deben almacenarse en texto plano. Los datos de acceso necesarios para evaluar el sistema deben estar documentados en la entrega.

5. Interfaz

La aplicación debe presentar una estructura integrada, con navegación entre sus módulos. Se sugiere un menú lateral con las siguientes secciones:

  • Ventas.
  • Productos y stock.
  • Clientes y cuentas corrientes.
  • Administración de usuarios.

La interfaz debe ser coherente, legible y adaptable a distintos tamaños de pantalla. Debe informar errores y confirmaciones de manera clara, validar los datos ingresados y facilitar las tareas habituales del usuario.

Alcance del ejercicio

  • Una única empresa, un único depósito y una única moneda: pesos argentinos.
  • Una sola forma de pago por venta; sin pagos combinados, cuotas, intereses ni asignación de un pago a una factura concreta. Los pagos reducen el saldo global del cliente.
  • Sin impuestos, descuentos, devoluciones ni anulación o edición de ventas y pagos confirmados. Los comprobantes y movimientos se conservan como historial.
  • La baja de productos y usuarios es lógica (estado inactivo). No se requiere eliminar clientes.
  • La distinción básica entre administrador y operador es necesaria. Los roles y permisos configurables, los gráficos y la impresión son mejoras opcionales.
  • El mockup ilustra pantallas y flujos con datos ficticios; sus simulaciones no sustituyen la persistencia, la autenticación ni las validaciones del servidor.

Requerimientos técnicos

  • Desarrollar una aplicación web utilizando JavaScript o TypeScript y React. Se puede utilizar Next.js o una solución equivalente que cumpla con los requisitos.
  • Implementar la lógica del servidor y el acceso a datos de manera que las validaciones importantes —por ejemplo, la disponibilidad de stock y el registro de la venta— también se realicen en el servidor.
  • Utilizar una base de datos persistente para productos, clientes, ventas, movimientos de stock, cuentas corrientes y usuarios.
  • Organizar el proyecto separando claramente la interfaz, la lógica de la aplicación y el acceso a los datos.
  • Publicar la aplicación y su base de datos de manera que el sistema pueda utilizarse desde internet y conserve la información entre sesiones.
  • Se pueden utilizar bibliotecas y herramientas como Tailwind CSS, Drizzle y Chart.js cuando resulten apropiadas.

Entrega

Se debe presentar:

  1. El código fuente completo del proyecto.
  2. Un archivo README.md que incluya:
    • Una descripción de la aplicación y las tecnologías utilizadas.
    • Las instrucciones para instalarla y ejecutarla localmente.
    • La configuración necesaria para conectar la base de datos, crear las tablas e inicializar el primer administrador.
    • El enlace a la aplicación publicada.
    • Los datos de acceso para la evaluación.
    • Las funcionalidades implementadas y, si corresponde, las pendientes.
  3. La aplicación funcionando tanto en la máquina de desarrollo como en su versión publicada.

La aplicación publicada debe contar con datos de ejemplo suficientes para probar sus principales funciones. Las credenciales privadas y las claves de acceso a servicios no deben incluirse en el código fuente.

Criterios de evaluación

Se evaluarán especialmente:

  • El cumplimiento y funcionamiento de los módulos solicitados.
  • La correcta integración entre ventas, stock y cuentas corrientes.
  • La persistencia y consistencia de los datos.
  • Las validaciones y el manejo de errores.
  • La claridad y organización del código.
  • La calidad y facilidad de uso de la interfaz.
  • La documentación y el funcionamiento de la versión publicada.
  • La capacidad de explicar y defender las decisiones tomadas.

Funcionalidades opcionales

Una vez completados los requisitos principales, se pueden incorporar mejoras como:

  • Un panel inicial con indicadores de ventas, productos con stock bajo y saldos pendientes.
  • Gráficos de ventas mediante Chart.js.
  • Filtros de ventas por fecha, cliente o forma de pago.
  • Impresión del comprobante.
  • Roles adicionales y permisos configurables.

El prototipo es orientativo y no reemplaza la implementación de las funcionalidades solicitadas.

Segundo parcial / Documentación técnica

API REST de referencia

Rutas, datos y reglas para implementar las funcionalidades del sistema.

Este documento propone una API para implementar las funcionalidades del segundo parcial. Los nombres de rutas y campos pueden adaptarse, siempre que la aplicación cumpla el enunciado. La API es una guía de diseño: no está implementada en el mockup.

Convenciones

  • Las rutas tienen como prefijo /api.
  • Las solicitudes y respuestas con contenido usan JSON y Content-Type: application/json.
  • Los identificadores de los ejemplos son enteros. Las fechas y horas se expresan en ISO 8601, por ejemplo 2026-10-29T14:30:00Z.
  • Los importes se representan en centavos enteros. Por ejemplo, 650000 equivale a $ 6.500,00. Los nombres de estos campos terminan en Centavos.
  • Las cantidades de productos y movimientos son números enteros positivos; el stock puede ser cero.
  • Los listados devuelven { "datos": [...] }. El parámetro q es opcional y permite buscar según los campos indicados en cada recurso.
  • Una respuesta exitosa sin contenido usa 204 No Content y no devuelve JSON.

Contrato común y permisos

  • Todos los endpoints, excepto POST /api/sesion, requieren sesión. Solo los administradores pueden usar /api/usuarios y /api/usuarios/:id; el resto está disponible para cualquier usuario activo.
  • Los PATCH aceptan un objeto JSON parcial: un campo omitido conserva su valor. null solo se admite en campos opcionales, como teléfono y correo. Se valida el objeto resultante, no únicamente los campos enviados.
  • Se rechazan con 422 campos desconocidos, campos de solo lectura o tipos incorrectos. El servidor asigna id, usuarioId (desde la sesión), número de comprobante y fecha de ventas y movimientos. No se acepta stock actualizado directamente ni totales calculados por el cliente.
  • En creación, los campos de los ejemplos son obligatorios salvo los identificados como opcionales. clienteId debe enviarse como null para consumidor final. observacion, telefono y correo pueden omitirse o ser null; el cliente debe conservar al menos un contacto.
  • Los textos obligatorios no pueden quedar vacíos después de quitar espacios. Importes y cantidades deben ser enteros dentro del rango seguro de la implementación, incluidos los resultados de sumas y multiplicaciones. No se aceptan números decimales en campos en centavos.
  • La búsqueda q no distingue mayúsculas ni acentos; vacía devuelve todos los registros. El acceso de usuario se normaliza quitando espacios y sin distinguir mayúsculas. El código de producto es único sin distinguir mayúsculas.
  • Para este volumen de ejercicio, los listados no requieren paginación. Productos, clientes y usuarios se ordenan por nombre e identificador; ventas y movimientos por fecha e identificador descendentes. activo admite true y false; si se omite, incluye ambos estados.
  • Los importes que muestra la interfaz están en pesos: se convierten a centavos antes de llamar la API. Las fechas y horas ingresadas se convierten desde la zona local a ISO 8601 con zona; al mostrarlas se convierten a la zona del comercio.
  • 404 se aplica a cualquier identificador referenciado que no exista. 409 se utiliza para acceso o código duplicado y conflictos de stock o saldo; 422, para otras violaciones de validación. Las respuestas de creación incluyen Location con la ruta del recurso cuando exista una ruta de consulta individual.

Errores

Los errores devuelven un código HTTP apropiado y un cuerpo como el siguiente:

{
  "error": {
    "codigo": "STOCK_INSUFICIENTE",
    "mensaje": "No hay stock suficiente para Café molido 250 g.",
    "detalles": { "productoId": 1, "disponible": 3, "solicitado": 5 }
  }
}
EstadoUso
400 Bad RequestJSON inválido o solicitud mal formada.
401 UnauthorizedFalta una sesión válida o las credenciales son incorrectas.
403 ForbiddenEl usuario no tiene permiso para la operación.
404 Not FoundEl recurso no existe.
409 ConflictConflicto con el estado actual, como stock insuficiente o código duplicado.
422 Unprocessable ContentDatos bien formados que no cumplen las reglas de validación.
500 Internal Server ErrorError inesperado del servidor; no se deben exponer detalles internos.

Los nombres de códigos de error incluidos son ejemplos; deben mantenerse consistentes en toda la aplicación.

Autenticación y usuarios

Las operaciones siguientes requieren una sesión válida, excepto el inicio de sesión. El servidor debe verificar en cada solicitud que el usuario siga activo. En esta propuesta se utiliza una cookie de sesión HttpOnly, Secure en producción y SameSite=Lax o más restrictiva. Se debe usar HTTPS en producción y protección CSRF del framework, o una comprobación estricta de origen con una estrategia equivalente; SameSite por sí solo no reemplaza esa protección. La sesión debe expirar, invalidarse al cerrar sesión y renovarse al iniciar sesión. La creación y modificación de usuarios está reservada al administrador.

El primer administrador se crea mediante un comando o proceso de inicialización documentado, sin un endpoint de registro público. Su contraseña se configura fuera del repositorio. No se permite desactivar ni quitar el perfil al último administrador activo (409).

Las respuestas de usuarios nunca incluyen la contraseña ni su representación almacenada.

Iniciar sesión

POST /api/sesion

{ "acceso": "ana@ejemplo.com", "contrasena": "contraseña-de-ejemplo" }

Respuesta: 200 OK, crea la sesión y establece la cookie.

{
  "usuario": {
    "id": 1,
    "nombre": "Ana Martínez",
    "acceso": "ana@ejemplo.com",
    "administrador": true,
    "activo": true
  }
}

Si las credenciales no son válidas o el usuario está inactivo, responde 401.

Consultar la sesión actual

GET /api/sesion

Devuelve 200 con el mismo objeto usuario o 401 si no hay sesión válida.

Cerrar sesión

DELETE /api/sesion

Invalida la sesión y responde 204.

Listar usuarios

GET /api/usuarios?q=lucia

Requiere administrador. La búsqueda puede incluir nombre y acceso.

{
  "datos": [
    { "id": 2, "nombre": "Lucía Pérez", "acceso": "lucia@ejemplo.com", "administrador": false, "activo": true }
  ]
}

Obtener un usuario

GET /api/usuarios/2

Requiere administrador. Devuelve 200 con el objeto de usuario o 404.

Crear un usuario

POST /api/usuarios

Requiere administrador. El acceso debe ser único y la contraseña debe almacenarse mediante un hash seguro para contraseñas.

{
  "nombre": "Lucía Pérez",
  "acceso": "lucia@ejemplo.com",
  "contrasena": "contraseña-de-ejemplo",
  "administrador": false,
  "activo": true
}

Respuesta: 201 Created, con el usuario creado sin contraseña. Un acceso duplicado produce 409.

Modificar un usuario

PATCH /api/usuarios/2

Requiere administrador. Se envían solo los campos a modificar. Los campos editables son nombre, acceso, administrador y activo. El cambio y la recuperación de contraseñas quedan fuera de esta API mínima; una ampliación debe invalidar las sesiones afectadas.

{ "nombre": "Lucía Pérez", "activo": false }

Respuesta: 200 OK, con el usuario actualizado sin contraseña. La desactivación debe impedir su acceso posterior, incluso si ya tenía una sesión abierta.

Productos

Un producto incluye id, codigo, nombre, precioVentaCentavos, stockActual y activo. El código debe ser único y el precio de venta, positivo. El stock se modifica mediante movimientos o ventas, no con la edición general del producto.

Listar productos

GET /api/productos?q=cafe

La búsqueda incluye código y nombre. El parámetro opcional activo=true permite limitar el listado a productos activos.

{
  "datos": [
    { "id": 1, "codigo": "CAF-001", "nombre": "Café molido 250 g", "precioVentaCentavos": 650000, "stockActual": 24, "activo": true }
  ]
}

Obtener un producto

GET /api/productos/1

Devuelve 200 con el producto o 404.

Crear un producto

POST /api/productos

{
  "codigo": "CAF-001",
  "nombre": "Café molido 250 g",
  "precioVentaCentavos": 650000,
  "stockInicial": 24,
  "activo": true
}

Respuesta: 201 Created, con el producto creado. En una única transacción, el servidor crea el producto y registra el stock inicial como un movimiento de entrada cuando es mayor que cero. El stock inicial no puede ser negativo.

Modificar un producto

PATCH /api/productos/1

{ "nombre": "Café molido 250 g", "precioVentaCentavos": 690000, "activo": true }

Los únicos campos editables son codigo, nombre, precioVentaCentavos y activo. stockInicial solo se acepta en la creación.

Respuesta: 200 OK, con el producto actualizado. La desactivación se realiza mediante activo: false; el producto permanece en el historial. Las modificaciones no alteran los detalles de ventas anteriores.

Movimientos de stock

Consultar movimientos

GET /api/movimientos-stock?productoId=1

productoId es opcional. Cada movimiento indica su origen; los movimientos de una venta incluyen el identificador de la venta.

{
  "datos": [
    {
      "id": 15,
      "fecha": "2026-10-29T14:30:00Z",
      "productoId": 1,
      "productoNombre": "Café molido 250 g",
      "detalleVentaId": 81,
      "tipo": "SALIDA",
      "cantidad": 2,
      "motivo": "Venta #42",
      "origen": "VENTA",
      "ventaId": 42,
      "usuarioId": 1
    }
  ]
}

Para movimientos manuales, origen es MANUAL y ventaId es null. La entrada inicial se identifica con origen INICIAL y también tiene ventaId igual a null. El identificador de una venta se obtiene a través de detalleVentaId; no hace falta duplicarlo en la tabla de movimientos. productoNombre se obtiene del catálogo para mostrar la lista. En un movimiento de origen VENTA, producto, cantidad y usuario deben corresponder al detalle y su venta; solo lo crea la operación de venta. INICIAL solo lo crea el alta de producto. La API manual solo crea origen MANUAL y también puede ajustar productos inactivos.

Registrar una entrada o salida manual

POST /api/movimientos-stock

{ "productoId": 1, "tipo": "ENTRADA", "cantidad": 10, "motivo": "Ingreso de mercadería" }

Respuesta: 201 Created, con el movimiento creado y el stock resultante:

{
  "movimiento": { "id": 16, "productoId": 1, "productoNombre": "Café molido 250 g", "detalleVentaId": null, "tipo": "ENTRADA", "cantidad": 10, "motivo": "Ingreso de mercadería", "origen": "MANUAL", "ventaId": null, "usuarioId": 1, "fecha": "2026-10-29T15:00:00Z" },
  "stockActual": 34
}

tipo admite ENTRADA o SALIDA. La cantidad debe ser positiva y el motivo obligatorio. Una salida que supere el stock disponible responde 409 y no genera ningún movimiento. El registro y la actualización del stock deben realizarse en una misma transacción.

Listar clientes

GET /api/clientes?q=gonzalez

{
  "datos": [
    { "id": 7, "nombre": "María González", "documento": "28.456.123", "telefono": null, "correo": "maria@ejemplo.com", "saldoCentavos": 2720000 }
  ]
}

Obtener un cliente

GET /api/clientes/7

Devuelve 200 con el cliente o 404.

Crear un cliente

POST /api/clientes

{ "nombre": "María González", "documento": "28.456.123", "telefono": null, "correo": "maria@ejemplo.com" }

Respuesta: 201 Created, con el cliente creado. Se requiere nombre, identificación y al menos un dato de contacto. La respuesta incluye saldoCentavos: 0. El cliente recién creado puede seleccionarse en una venta, sin necesidad de reiniciarla.

Modificar un cliente

PATCH /api/clientes/7

{ "telefono": "381 555-0123", "correo": "maria@ejemplo.com" }

Los campos editables son nombre, documento, telefono y correo.

Respuesta: 200 OK, con el cliente actualizado. Debe conservarse al menos un dato de contacto y no deben modificarse los datos de comprobantes anteriores.

Ventas y comprobantes

Las formas de pago admitidas son CONTADO, TARJETA y CUENTA_CORRIENTE. Para consumidor final se envía clienteId: null. La cuenta corriente requiere un cliente registrado.

Listar ventas

GET /api/ventas

{
  "datos": [
    { "id": 42, "numero": 42, "clienteId": 7, "fecha": "2026-10-29T14:30:00Z", "clienteNombre": "María González", "formaPago": "CUENTA_CORRIENTE", "totalCentavos": 1720000 }
  ]
}

Se pueden incorporar filtros por fecha, cliente o forma de pago como mejora opcional.

Registrar una venta

POST /api/ventas

{
  "clienteId": 7,
  "formaPago": "CUENTA_CORRIENTE",
  "productos": [
    { "productoId": 1, "cantidad": 2 },
    { "productoId": 2, "cantidad": 1 }
  ]
}

El servidor debe obtener los precios vigentes, calcular los importes, verificar que los productos estén activos y comprobar el stock. No debe confiar en precios o totales enviados por el navegador. Si un mismo producto aparece más de una vez, debe sumar sus cantidades y crear un solo detalle para ese producto antes de comprobar las existencias. Se conservan copias del nombre y documento del cliente y de la descripción y precio del producto; no se reconstruyen desde el catálogo al consultar un comprobante.

En una única transacción, debe guardar el comprobante y sus detalles, descontar las existencias y registrar los movimientos de salida. Si cualquier paso falla, no debe quedar aplicada ninguna parte de la operación. Las comprobaciones y actualizaciones de stock deben protegerse frente a ventas simultáneas, por ejemplo mediante una actualización condicional de stock dentro de una transacción que se revierte si no se pudo descontar todo. La deuda aparece al guardar la venta en cuenta corriente: no se inserta otra deuda duplicada. La numeración debe ser única bajo concurrencia; no usar MAX(numero) + 1 sin protección.

Respuesta: 201 Created, con el comprobante completo, usando el formato de GET /api/ventas/42 que se muestra a continuación.

Una venta sin productos o con cantidades inválidas responde 422; un producto inexistente responde 404; un producto inactivo o stock insuficiente responde 409. Una cuenta corriente sin cliente responde 422.

Consultar el comprobante

GET /api/ventas/42

{
  "id": 42,
  "numero": 42,
  "fecha": "2026-10-29T14:30:00Z",
  "usuarioId": 1,
  "clienteId": 7,
  "clienteNombre": "María González",
  "clienteDocumento": "28.456.123",
  "formaPago": "CUENTA_CORRIENTE",
  "productos": [
    { "productoId": 1, "descripcion": "Café molido 250 g", "cantidad": 2, "precioUnitarioCentavos": 650000, "subtotalCentavos": 1300000 },
    { "productoId": 2, "descripcion": "Té en hebras 100 g", "cantidad": 1, "precioUnitarioCentavos": 420000, "subtotalCentavos": 420000 }
  ],
  "totalCentavos": 1720000
}

Para consumidor final, clienteId es null, clienteNombre es "Consumidor final" y clienteDocumento puede ser null. El comprobante es interno y no fiscal. La impresión puede realizarse desde la interfaz utilizando estos datos; no requiere un endpoint específico.

Cuenta corriente y pagos

El saldo se calcula como la suma de ventas en CUENTA_CORRIENTE del cliente menos los pagos registrados. Las ventas de contado y tarjeta no forman parte de la cuenta.

Consultar cuenta corriente

GET /api/clientes/7/cuenta-corriente

Devuelve el saldo y los movimientos en orden de fecha descendente. Los importes de los movimientos son positivos; tipo indica si aumentan o reducen la deuda.

  "clienteId": 7,
  "saldoCentavos": 2720000,

    { "tipo": "PAGO", "fecha": "2026-10-25T12:00:00Z", "pagoId": 8, "importeCentavos": 500000, "observacion": "Pago parcial" },
    { "tipo": "VENTA", "fecha": "2026-10-20T12:00:00Z", "ventaId": 31, "numeroComprobante": 31, "importeCentavos": 1500000 }

La respuesta también puede acompañarse con los datos de GET /api/clientes/:id para mostrar nombre y contacto. Un cliente inexistente responde 404. Un cliente sin movimientos tiene saldo cero y un arreglo vacío.

Registrar un pago

POST /api/clientes/7/pagos

{ "fecha": "2026-10-29T15:00:00Z", "importeCentavos": 500000, "observacion": "Pago parcial" }

Respuesta: 201 Created:

{
  "pago": { "id": 9, "clienteId": 7, "usuarioId": 1, "fecha": "2026-10-29T15:00:00Z", "importeCentavos": 500000, "observacion": "Pago parcial" },
  "saldoCentavos": 2220000
}

El importe debe ser positivo y no puede superar el saldo adeudado. Una fecha válida es obligatoria y la observación es opcional. Si el pago supera el saldo, responde 409 y no se registra. La comprobación del saldo y el registro deben protegerse frente a pagos simultáneos, bloqueando o serializando las operaciones sobre esa cuenta dentro de una transacción. Una fecha futura no es válida. Esta API registra un pago recibido, no procesa tarjetas ni transferencias.

Límites y operaciones de interfaz

No hay borrado físico ni edición de ventas, pagos o movimientos confirmados en este alcance. Los cambios de stock se registran como nuevos movimientos con motivo; los productos y usuarios se desactivan. Las búsquedas, los borradores de venta, el cálculo visual de subtotales y la impresión no requieren endpoints adicionales. El servidor vuelve a calcular y validar al confirmar.

La interfaz debe deshabilitar el botón mientras confirma una venta o pago. Tras una respuesta incierta por corte de red, se debe consultar el historial antes de reenviar; para permitir reintentos automáticos seguros se puede incorporar una clave de idempotencia como ampliación.

El panel de ejemplo calcula indicadores sobre los listados recibidos. “Stock bajo” usa un umbral ilustrativo de 3 unidades; no agrega un requisito obligatorio de stock mínimo. Gráficos, filtros avanzados, paginación y roles configurables son ampliaciones.

Relaciones y cardinalidades

Cada línea conecta dos entidades. Debajo de cada nombre se indica cuántos registros de la otra entidad pueden corresponderle: 0..1 significa cero o uno; 0..N, cero o muchos; 1..N, uno o muchos.

USUARIOCada usuario: 0..N ventas
VENTACada venta: 1 usuario
CLIENTECada cliente: 0..N ventas
VENTACada venta: 0..1 cliente
VENTACada venta: 1..N detalles
DETALLE_VENTACada detalle: 1 venta
PRODUCTOCada producto: 0..N detalles
DETALLE_VENTACada detalle: 1 producto
PRODUCTOCada producto: 0..N movimientos
MOVIMIENTO_STOCKCada movimiento: 1 producto
USUARIOCada usuario: 0..N movimientos
MOVIMIENTO_STOCKCada movimiento: 1 usuario
DETALLE_VENTACada detalle confirmado: 1 salida
MOVIMIENTO_STOCKCada movimiento: 0..1 detalle
CLIENTECada cliente: 0..N pagos
PAGOCada pago: 1 cliente
USUARIOCada usuario: 0..N pagos
PAGOCada pago: 1 usuario

El cliente es opcional en una venta para permitir consumidor final. Los movimientos manuales y de stock inicial no referencian un detalle de venta; una salida generada por una venta se vincula con su detalle.

Para asegurar una sola salida por detalle, detalle_venta_id debe ser único cuando tenga valor. La lógica de confirmación debe crear esa salida junto con el detalle, dentro de la misma transacción: la clave foránea y la unicidad por sí solas no garantizan que exista.

Ventas y clientes

Una venta puede tener un cliente registrado o corresponder a consumidor final. Un usuario registra muchas ventas; cada venta contiene uno o más detalles.

Productos y stock

Un producto puede aparecer en muchos detalles y tener muchos movimientos. Cada detalle de venta genera una salida de stock. Los movimientos manuales y de stock inicial no tienen detalle de venta; el campo origen distingue los tres casos.

Pagos y cuenta corriente

Un cliente puede tener muchos pagos; cada pago lo registra un usuario. El saldo se calcula como las ventas en cuenta corriente menos los pagos.

Historial y consistencia

Las ventas conservan los datos del cliente y los precios y descripciones utilizados. La venta, sus detalles y las salidas de stock deben registrarse en una misma transacción.

El modelo de referencia y la API utilizan centavos enteros. Los nombres en snake_case del modelo corresponden a los nombres en camelCase de la API. Los importes deben ser enteros no negativos; precio y pago deben ser mayores que cero.

Restricciones del modelo

  • Claves primarias y foráneas enteras. Las claves foráneas son obligatorias salvo cliente_id en VENTA y detalle_venta_id en MOVIMIENTO_STOCK. No eliminar registros referenciados por el historial.
  • Código de producto, acceso de usuario y número de comprobante únicos. En DETALLE_VENTA, el par (venta_id, producto_id) es único porque se agrupan las cantidades repetidas.
  • Cantidad entera positiva; stock_actual entero no negativo. El stock inicial también genera un movimiento: stock_actual debe coincidir con entradas menos salidas. Se actualizan juntos en una transacción.
  • tipo admite ENTRADA o SALIDA; origen admite INICIAL, MANUAL o VENTA. INICIAL requiere ENTRADA y detalle nulo. MANUAL requiere detalle nulo. VENTA requiere SALIDA y detalle; su producto, cantidad y usuario deben coincidir con el detalle y la venta.
  • forma_pago admite CONTADO, TARJETA y CUENTA_CORRIENTE. La cuenta corriente exige cliente_id. Los nombres, identificación, descripción y precios de la venta son copias históricas.
  • subtotal_centavos = cantidad × precio_unitario_centavos; total_centavos es la suma de detalles. La aplicación impide ventas vacías y crea una salida por detalle al confirmar.
  • Saldo de cliente: ventas en cuenta corriente menos pagos. No se almacena una deuda adicional ni se edita el saldo. Los pagos se validan contra el saldo dentro de una operación serializada por cliente.
  • Fechas y horas con zona normalizadas en UTC; activo y administrador son booleanos. El correo y teléfono pueden ser nulos, pero al menos uno debe tener contenido.

Las sesiones son infraestructura de autenticación. El diagrama muestra las entidades del negocio; el framework puede usar su propio almacén de sesiones con usuario, expiración e invalidación.
