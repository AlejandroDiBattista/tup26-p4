La idea

Un modelo de lenguaje recibe texto y devuelve texto. No puede abrir un archivo ni guardar nada en tu disco. Pero puede hacer algo más modesto: pedir que alguien lo haga por él.

Un asistente de programación (también llamado agente) es un programa común que conversa con el modelo. Cuando el modelo pide una herramienta, el programa la ejecuta y le devuelve el resultado. El modelo decide; nuestro programa actúa.

Todo el programa se apoya en tres ideas:

  1. Una conversación guardada en un array de mensajes (paso 4).
  2. Herramientas que el modelo puede pedir. Las describimos para él y las implementamos para nosotros (pasos 5 a 7).
  3. Un bucle que consulta al modelo, ejecuta lo que pide y vuelve a consultar hasta que responde con texto (paso 8).

Cómo está organizado el archivo

Son 132 líneas en un solo archivo, divididas en cuatro bloques. Casi la mitad son las herramientas, y la mayor parte de eso es la descripción que lee el modelo.

Sin dependencias

Todo lo que usamos viene con Node: fetch para hablar con la API, fs para los archivos, readline para la consola y util para los colores. No hay npm install ni carpeta node_modules. El prefijo node: de los import (como en node:fs) indica justamente eso: es un módulo de Node, no un paquete externo.

Módulos ES

"type": "module" le dice a Node que los archivos .js usan import en lugar de require. Además habilita dos cosas que el programa necesita: import.meta.url (paso 2) y usar await fuera de una función (paso 9).

La clave es un secreto

Con tu clave, cualquiera puede usar la API a tu nombre y gastar tu saldo. Por eso no va en el código sino en .env, y .env va en .gitignore para que nunca llegue al repositorio.

Variables de entorno

process.env es un objeto con las variables de entorno del proceso. process.loadEnvFile(ruta) lee un archivo .env y agrega cada línea NOMBRE=valor a ese objeto. Por eso después podemos leer process.env.OPENAI_API_KEY. Antes esto requería el paquete dotenv; desde Node 20.12 viene incluido.

Rutas relativas al archivo

import.meta.url es la dirección del propio archivo: file:///…/clase/asistente.js. new URL(".env", import.meta.url) resuelve .env a partir de ahí y da file:///…/clase/.env. Si escribiéramos solo ".env", Node lo buscaría en la carpeta desde donde ejecutaste el comando, que puede ser otra.

La clave en los ejemplos del navegador

En los ejemplos HTML, usamos obtenerApiKey() en lugar de leer una variable de entorno. Primero busca OPENAI_API_KEY en localStorage; si falta, la solicita con prompt, quita los espacios de los extremos y la guarda. Si cancelás o dejás el campo vacío, detiene la consulta sin guardar nada.

La función se llama al enviar la consulta, no al abrir la página. Los ejemplos comparten la clave cuando se sirven desde el mismo origen (protocolo, host y puerto), según localStorage en MDN. Para cambiarla, ejecutá localStorage.removeItem("OPENAI_API_KEY") en la consola del navegador y volvé a consultar. El programa de terminal de este tutorial conserva su configuración con .env.

Hablar con el modelo por REST

La API de OpenAI es una API REST: le hablamos con pedidos HTTP comunes, igual que un navegador le pide una página a un servidor. Cada consulta al modelo es un pedido como este:

Tiene cuatro partes:

  • El método: POST, porque enviamos datos.
  • La dirección: el endpoint de chat completions.
  • Los encabezados: en qué formato mandamos los datos y quiénes somos. Bearer significa “portador”: quien porta la clave tiene acceso.
  • El cuerpo: los datos, en JSON.

La API contesta con un JSON como este. De todo eso solo nos interesa choices[0].message: el mensaje que escribió el modelo.

fetch, await y JSON

fetch devuelve una promesa: el pedido viaja por la red y la respuesta llega más tarde. await espera a que llegue. Hay dos esperas: la primera recibe la respuesta (estado y encabezados) y la segunda, respuesta.json(), termina de leer el cuerpo.

HTTP transporta texto. JSON.stringify convierte nuestro objeto en texto para enviarlo, y respuesta.json() hace lo inverso con lo que llega.

Cuando algo falla

Si la clave es incorrecta o el pedido tiene un problema, la API no devuelve choices sino {"error": {"message": "…"}}. La línea if (datos.error) throw … muestra ese mensaje tal cual, en vez de un confuso Cannot read properties of undefined.

¿Para qué es reasoning_effort?

Con el modelo que usamos, la API no admite herramientas en chat completions si el modelo razona antes de responder. Hay dos salidas: usar otro endpoint (/v1/responses) o desactivar el razonamiento con "none". Elegimos la segunda porque no cambia nada más. Si usás un modelo que no acepta este parámetro, borrá esa línea.

La conversación es un array

Hay un detalle de la API que define todo el diseño: no tiene memoria. Cada pedido es independiente, y el modelo no recuerda nada de los anteriores.

¿Cómo mantiene entonces una conversación? En cada pedido le mandamos la conversación completa. La memoria del asistente es un array que vamos agrandando:

Cada mensaje tiene un role (quién lo dice) y un contenido. Hay cuatro roles:

RolLo escribePara qué
systemNosotros, una vezInstrucciones generales: qué es, qué puede hacer, cómo responder.
userLa personaLo que escribe en la consola.
assistantEl modeloSu respuesta: texto o pedidos de herramientas.
toolNuestro programaEl resultado de ejecutar una herramienta.

Una API sin estado

Una API sin estado (stateless) no guarda nada entre pedidos. Es más simple de construir y de escalar, pero traslada la responsabilidad al cliente: nosotros guardamos la historia y la reenviamos. Consecuencia práctica: cada pedido es más largo que el anterior, y el costo se calcula según la cantidad de texto (tokens) que se envía.

Describir las herramientas

El modelo no ve nuestro código. Para que sepa qué herramientas existen, se las describimos: nombre, para qué sirve y qué parámetros recibe. Esa descripción viaja en cada pedido, en el campo tools.

Es la parte más larga del programa, pero son solo datos. Cada herramienta tiene tres campos:

  • name: debe coincidir con el nombre de nuestra función. En el paso 7 usamos ese nombre para encontrarla.
  • description: para qué sirve y cuándo conviene usarla.
  • parameters: qué datos necesita.

JSON Schema

parameters usa JSON Schema, un formato estándar para describir la forma de un JSON. Acá dice: “los argumentos son un objeto (type: "object") con una propiedad ruta de tipo texto, y es obligatoria (required)”. El modelo sigue ese esquema cuando arma los argumentos de su pedido.

La descripción también es un prompt

El modelo decide cuándo usar una herramienta leyendo su descripción. Por eso escribirArchivo aclara “Crea o reemplaza” y contenido pide el “texto completo”: así el modelo sabe que, si escribe, pisa lo que había.

Usamos las versiones síncronas (readFileSync y writeFileSync) porque son las más fáciles de leer. Bloquean el programa mientras trabajan, pero acá no importa: la persona está esperando la respuesta de todos modos.

Desestructuración

function leerArchivo({ ruta }) recibe un objeto y extrae su propiedad ruta. Coincide con lo que manda el modelo: { "ruta": "suma.js" }. Así no hace falta escribir argumentos.ruta dentro de la función.

Siempre devolver texto

El resultado vuelve al modelo como contenido de un mensaje, y ese contenido es texto. Con "utf8", readFileSync devuelve un string; sin esa opción devolvería bytes (un Buffer). escribirArchivo devuelve "Archivo guardado" para que el modelo sepa que funcionó.

Un diccionario de funciones

{ leerArchivo, escribirArchivo } es la forma abreviada de { leerArchivo: leerArchivo, escribirArchivo: escribirArchivo }. Es un objeto que asocia cada nombre con su función. En el próximo paso lo usamos para llamar a una herramienta a partir de su nombre, sin if ni switch.

Solo el camino feliz

Si el archivo no existe, readFileSync lanza un error y el programa termina. Es una decisión deliberada para que el código se entienda. En Para seguir está cómo resolverlo.

El bucle del agente

Este es el corazón del programa. Una sola pregunta puede requerir varias herramientas en secuencia: leer un archivo, escribir otro, volver a leer para verificar. No sabemos de antemano cuántas, así que usamos un bucle:

En palabras:

  1. Consultar al modelo con toda la conversación.
  2. Guardar su respuesta en mensajes.
  3. Si no pidió herramientas, terminó: devolver el texto.
  4. Si pidió, ejecutar cada una, guardar los resultados y volver al punto 1.

while (true) parece peligroso, pero la salida está garantizada por el return: en cuanto el modelo responde sin pedir herramientas, la función termina.

El orden importa

Primero va el mensaje del modelo con tool_calls y después un mensaje tool por cada pedido. Por eso hacemos mensajes.push(mensaje) antes del for. Si falta alguno de los dos, la API responde con un error.

Por qué un for

tool_calls es un array. Muchas veces trae un solo pedido, pero el modelo puede pedir varios juntos (por ejemplo, leer tres archivos a la vez). El for…of los ejecuta todos.

La consola

Falta la parte que ve la persona: leer lo que escribe, pasárselo a responder y mostrar la respuesta. Es otro bucle:

readline

readline.createInterface conecta la entrada (process.stdin, el teclado) con la salida (process.stdout, la pantalla). consola.question(texto) muestra el texto y devuelve una promesa. Esa promesa se cumple cuando la persona presiona Enter, y trae la línea que escribió.

await fuera de una función

El bucle principal no está dentro de ninguna función async y, aun así, usa await. Funciona porque el archivo es un módulo ES (paso 1): en los módulos, Node permite await en el nivel superior (top-level await).

Cómo termina

Si la persona escribe salir, el break corta el bucle. Con Ctrl+C o Ctrl+D, la interfaz se cierra sola y el evento close termina el proceso con process.exit(). Sin esa línea, Node mostraría un error, porque question quedaba esperando una respuesta que nunca llega.

Dos bucles, uno dentro del otro

Darle color

El programa ya funciona, pero en la terminal todo se ve igual y cuesta distinguir lo que escribiste de lo que respondió el asistente. Node trae styleText en node:util para colorear texto sin instalar nada. Alcanza con cambiar tres líneas:

styleText(formato, texto) devuelve el mismo texto con los códigos de color incluidos. El formato puede ser un nombre ("cyan") o un array para combinar varios (["bold", "green"]). Lo que escribe la persona queda en el color normal de la terminal, así que se distingue de la respuesta.

Códigos ANSI

La terminal no entiende la palabra “cian”: entiende secuencias especiales. styleText("cyan", "hola") devuelve "\x1b[36mhola\x1b[39m". El primer código dice “empezá a escribir en cian” y el segundo, “volvé al color normal”. Si la salida no es una terminal (por ejemplo, si la redirigís a un archivo) o si está definida la variable NO_COLOR, styleText no agrega los códigos.

Para seguir

Tres ejercicios para practicar, de menor a mayor dificultad:

  1. Una herramienta nueva. Agregá listarArchivos, que devuelva los archivos de una carpeta con fs.readdirSync(ruta).join("\n"). Solo hay que tocar dos lugares: su descripción en herramientas y su implementación en funciones. El bucle no cambia.

  2. Errores que el modelo pueda ver. Si una herramienta falla, devolvé el error como resultado en lugar de cortar el programa. Así, si el archivo no existe, el modelo se entera y puede reaccionar (por ejemplo, preguntando otra ruta).

  3. Pedir permiso antes de escribir. En escribirArchivo, preguntá con consola.question si la persona acepta el cambio. Pista: la función pasa a ser async, así que ejecutarHerramienta y el for de responder tienen que esperar su resultado con await.
